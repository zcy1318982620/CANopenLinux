第 5 站 · 启动链路走读 —— 进程从开机到跑起来

工程：panasonic_canopen_agv —— 松下「実験用 AGV」双轮差速底盘，基于 CANopenNode V4 的 CANopen 从站（Linux 用户态 + SocketCAN，进程名 canopend）。

本篇定位：第 5 站 = 把整个进程从头到尾串一遍。前面第 1~4 站是「拆开看零件」，本站是「装回去看整机」——从命令行敲下 canopend can0 -i 1 -c stdio，到终端打出 posR/posL，中间到底经过哪些步骤、哪一步在哪、为什么这么排。

为什么先看启动链路？因为后面第 6 站（实时性）、第 7 站（里程计）都是往这条链上加东西。不知道链长什么样，就不知道该往哪儿插。

怎么读：本册以一个主文件（CO_main_basic.c）为主线，每段只回答：这段在干什么 → 关键函数传什么/返回什么 → 被谁调用 → 它调用了谁。不做字节级拆帧，重点看流程图。行号格式 文件:行号。

标记：★★★ 必会 / ★★ 重要 / ★ 知道即可。灰框=补充，红框=坑。

0. 一页地图：一个进程，四段 + 两条线程

先给一句话结论：main() 从头到尾就是「做准备 → 进一个大循环反复初始化 → 进一个小循环一直跑 → 收到退出信号就收摊」。CANopen 的全部功能都挂在这个骨架上。

5. reset 机制：为什么外面还套一层循环

这是全文件最容易看漏、又最体现 CANopen 设计思想的一点。CANopen 协议里，主站可以随时发 NMT 复位命令，让从站「重来一次」。本工程用两层循环来优雅应对：

两层循环与 reset 取值（CO_NMT_reset_cmd_t）

 外层 while(reset != APP && reset != QUIT && !endProgram)      :575
   │
   │   【准备：只做一次】
   │   注 意：app_programStart()、CO_new()、建线程 都在外层之外/首次路径上
   │
   └─ 内层 while(reset == NOT && !endProgram)                  :795
         │   正常运行：主线程 + RT 线程一直转
         │
         └─ reset = CO_process(...)   ← 主线程每轮把它「取回来」
                 │
                 ├─ reset == NOT    → 继续跑（最常见）
                 ├─ reset == COMM   → 内层退出 → 回外层 → ★重新初始化通信（③ 重来一遍）
                 └─ reset == APP    → 两层都退出 → 程序收摊（可选重启系统）
                     reset == QUIT → 两层都退出 → 直接结束

 两个关键点：
   · 收到 NMT "reset communication" → COMM → 只重跑 ③（CAN/LSS/CANopen/PDO 重初始化），
                                        ②（分配内存、建线程）不重做。
   · 收到 NMT "reset application"   → APP  → 直接退出进程（或按 -r 重启系统）。
   · firstRun 标志 (:719) 保证「建 RT 线程、初次设时间」只做一次，重初始化时不重复建线程。
表 5-1　三类 reset 的差别
reset 值谁触发本程序怎么反应
CO_RESET_NOT正常状态什么都不做，内层循环继续跑。
CO_RESET_COMMNMT「reset communication」/ 上电首次内层退出 → 回到外层重做初始化（重新建 CAN、CANopen、PDO），线程和内存不动。
CO_RESET_APP / CO_RESET_QUITNMT「reset node」/ 内部要求退出两层都退出 → 收摊（若 -r 且是 APP，则重启系统）。
这解释了 §3 的一个设计：为什么 app_programStart() 在外层循环之外、只调一次，而 app_communicationReset() 在外层循环之内、每次重初始化都调？因为前者是「写 OD 配置、挂钩子」（配一次就够，值还留在 OD 里），后者是「通信层面每次复位后要重做的事」。分工不同，位置就不同。

干啥SDO / NMT / 心跳 / EMCY / 时间 / 网关命令收 CAN 帧 / SYNC / PDO
优先级普通可由 -p 设成 SCHED_FIFO 实时
为什么偶尔发生、晚点无所谓周期性、要准时（AGV 控制靠它）

6.3 一个「事件等待器」是怎么工作的

两条线程都用 CO_epoll_wait() 阻塞等待，靠什么被叫醒？靠 CO_epoll_create()（:68）建的三样东西：

epoll_fd   多路等待器：同时盯着好几个"门"，任一个响就去处理
event_fd   通知门：别的线程/回调想立刻叫醒本线程时，往这写一个数（wakeupCallback :226）
timer_fd   定时门：每 timerInterval_us 响一次（主 100ms / RT 1ms）

流程：CO_epoll_wait 里做的三件事
   ① 睡眠等"门"响                :149  epoll_wait(…, -1)  ← -1 = 一直等到有事件
   ② 醒来算"这一觉睡了多久"        :154-156  → timeDifference_us（给 CANopen 算超时用）
   ③ 记录"这次是定时门响的吗"      :188  → timerEvent
   → 主循环/R​​T线程拿这些信息去决定"这一拍要不要处理 PDO/SYNC"
RT 线程里那句 if (!realtime || ep->timerEvent)（CO_epoll_interface.c:329）很关键：主线程调用时 realtime=false，每轮都处理；RT 线程调用时 realtime=true，只在定时门响（1ms 到点）时才处理 PDO/SYNC，其它唤醒（比如只是有 CAN 帧）只收帧、不跑 PDO 逻辑。这就是「PDO 严格按 1ms 节拍走」的实现。

8. 小结 · 自测 · 衔接

8.1 一页复盘

① main() = 四段：读参数 → 做准备(只一次) → 通信复位循环(可重做) → 正常运行循环。
② 准备阶段的重点是：CO_new 分配「两套」对象（左右电机）、app_programStart 写 PDO 配置+挂钩子、
   建三个 epoll（主 100ms / RT 1ms / 命令口）。
③ 通信复位循环 = 第 1~4 站初始化的集合：
   CO_CANinit(第1站) → CO_LSSinit(第2站) → CO_CANopenInit(第2/3站)
   → CO_CANopenInitPDO(第4站) → CO_CANsetNormalMode(开闸)。
④ 外层 while + reset 值，实现「NMT 复位命令 → 只重初始化通信、不重启进程」；
   firstRun 保证线程只建一次。
⑤ 运行时分两条线程：主线程 100ms 跑 SDO/NMT/心跳；RT 线程 1ms 跑收帧/SYNC/PDO。
⑥ 退出：置标志 → join RT 线程 → 应用收尾 → 关 epoll → 释放对象（可选重启）。
