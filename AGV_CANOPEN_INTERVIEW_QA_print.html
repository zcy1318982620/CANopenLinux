§1 CAN 与 CANopen 协议

Q1CAN 和 CANopen 有什么区别？
CAN 是"车"，CANopen 是"交通规则"。CAN 只定义了物理层和数据链路层（帧格式、仲裁、CRC、错误处理），它保证一帧报文能可靠送到，但不定义这帧是什么意思。CANopen 是建在 CAN 之上的应用层协议（CiA 301），定义了报文该怎么用：对象字典、SDO/PDO、NMT、心跳等。本工程里 SocketCAN 提供 CAN 层，CANopenNode 提供 CANopen 层。
Q2对象字典（OD）是什么？
一张用"16 位索引 + 8 位子索引"寻址的参数表。每一项记录数据类型、访问权限（RO/WO/RW）、是否可映射到 PDO，以及数据存在哪。所有 SDO/PDO 访问本质都是对 OD 的读/写。本工程有两套 OD：OD（右电机）和 OD_2nd（左电机），见 [application/OD.c](file:///home/zcy/Project/panasonic_canopen_agv/application/OD.c)。
Q3SDO 和 PDO 的区别？
SDO 慢而通用，PDO 快而专用。SDO 是点对点、有应答，可访问任意 OD 条目，适合配置和偶发数据；PDO 是广播式、无应答，只能传输预先映射好的条目，适合周期性实时数据。本工程位姿用 SDO 轮询（实现简单、够用）；若要低延迟上报，应改 TPDO 主动发送。
Q4PDO 映射怎么配置？
先清零、逐条填、再写回条数。通过通信参数（收 0x1400/0x1600、发 0x1800/0x1A00）和映射参数（0x1601/0x1A01）配置：把映射条数写 0 → 逐条写"哪个 index/subindex、多少位"→ 最后写回实际条数使其生效。本工程 TPDO 预留了 0x6040 + 0x60FF，但无人触发。
Q5NMT 状态机是怎样的？
初始化 → Pre-operational → Operational → Stopped。只有 Operational 状态才能收发 PDO；SDO 在任何状态都可用。NMT 命令由主站下发（广播 nodeid=0 或指定节点）。本工程网关的 start / stop / preop / reset node 就是发 NMT 命令。
Q6心跳（Heartbeat）和节点守护（Node Guarding）的区别？
一个是从站主动报、一个是主站轮着问。心跳是从站周期发送 0x700+nodeid（内容带状态），主站被动监测；节点守护是主站周期发远程帧、从站应答。工程上现在更推荐心跳（省总线）。本工程应开启 0x1017 心跳，让上位机能监测节点掉线。
Q7CAN 帧 ID 与优先级的关系？CANopen 怎么划分 ID？
ID 越小优先级越高。CANopen 用"功能码 + 节点号"划分：NMT 0x000、SYNC/EMCY 0x080、TPDO1 0x180+nodeid、RPDO1 0x200+nodeid、SDO 应答 0x580+nodeid、SDO 请求 0x600+nodeid、心跳 0x700+nodeid。所以紧急报文（EMCY）优先级天然高于常规数据。
Q8为什么第一站就能读到 0x6064？
因为电机驱动器是 CiA402 从站，0x6064 是它必实现的"实际位置"。CiA402 是 CANopen 的驱动/运动控制行规，规定了控制字 0x6040、状态字 0x6041、实际位置 0x6064 等。注意：0x6064 是单个电机的原始位置计数，不是车在世界里的 x,y,θ。

§2 嵌入式 Linux 与实时性

Q9为什么用 Linux 用户态跑 CANopen，而不是裸机 / RTOS？
为了复用成熟栈、开发快。CANopenNode V4 的 Linux 用户态版本 + SocketCAN，直接编成一个进程 canopend。好处：现成协议栈、能同时跑网络/网关/文件系统/日志；代价：Linux 默认调度不是硬实时，需要 SCHED_FIFO 等改造（第 6 站）。
Q10SocketCAN 是什么？
Linux 内核里的 CAN 子系统。它把 CAN 控制器抽象成一个网络接口（如 can0），用户态用标准 socket API（PF_CAN）收发帧，不用碰寄存器。本工程用户态直接对 can0 读写。
Q11你怎么提高这个系统的实时性？
四招：实时调度 + 绝对时间睡眠 + 锁内存 + 减阻塞。① 关键线程设 SCHED_FIFO 高优先级（本工程 RT 线程优先级 80）；② 用 clock_nanosleep(TIMER_ABSTIME) 按"绝对时刻"睡，避免误差累积；③ mlockall 锁内存避免缺页抖动；④ RT 周期里不做重活（尤其别 printf）。
Q12SCHED_FIFO 和 SCHED_OTHER 有什么区别？
前者是实时抢占调度，后者是桌面分时调度。SCHED_OTHER（CFS）会公平分时、可能被降级，适合普通任务；SCHED_FIFO 下同优先级先到先服务、高优先级可抢占低优先级、不做时间片轮转，能保证唤醒的确定性。实时任务必须用实时策略。
Q13什么是抖动（jitter）？怎么测？
抖动 = 实际唤醒时刻与理论时刻的偏差。记录每拍"实际 - 理论"的时间差，统计均值 / 最大值 / P99 / P999。用绝对时间睡眠可把误差从"逐拍累积漂移"变成"单次唤醒误差"。本工程有自研抖动统计，也可用 cyclictest 交叉验证（第 6 站）。
Q14为什么要多线程？主线程和 RT 线程各干什么？
隔离"确定性的活"和"不确定的活"。主线程跑 epoll 处理网络/网关（可能阻塞、耗时不定）；RT 线程管 1ms 周期任务（收发 PDO、跑里程计）。分开后，网络再忙也不会拖累节拍，实时性才有保障。
Q15 ★为什么位姿要加 CO_LOCK_OD？不加会怎样？
因为它是"RT 线程写、主线程读"的共享数据。RT 线程把位姿写进 OD 数组 0x6FFF，主线程（网关处理 SDO 读）同时读同一块内存。不加锁可能读到"改了一半"的数据。本工程未定义 CO_SINGLE_THREAD，所以 CO_LOCK_OD 是真正的 pthread_mutex 互斥量（不是空宏），见 [CO_driver_target.h:354-392](file:///home/zcy/Project/panasonic_canopen_agv/CO_driver_target.h#L354-L392)。
Q16为什么主循环用 epoll？
同时等多个 IO 且高效。epoll 是 Linux 的 IO 多路复用，能一次监听多个 fd（CAN 套接字 + 网关 TCP socket），无 select 的 fd 数量上限、也不用全量轮询。本工程 CO_epoll_wait 同时等待 CAN 和网关连接。
Q17什么是交叉编译？为什么需要？
在 x86 PC 上编出能在 ARM 板上跑的二进制。开发板和 PC 架构不同，必须用 ARM 工具链编译 canopend 再拷到板子运行。这是第 9 站的任务。

§3 电机 · 运动学 · 里程计

Q18差速轮 AGV 的正/逆运动学？
正解：由两轮速度求车体；逆解：反过来。设轮距 L，左右轮线速度 vL/vR，则车体线速度 v=(vR+vL)/2、角速度 ω=(vR−vL)/L。里程计是逆过程：由左右轮位移 ΔdR/ΔdL 得 Δd=(ΔdR+ΔdL)/2、Δθ=(ΔdR−ΔdL)/L（第 7 站）。
Q19里程计为什么用"中点法"？
为了把转弯时的圆弧近似得更准。若直接用当前 θ 算位移，转弯时会有线性误差。中点法用 θ_mid = θ + Δθ/2 处的方向乘位移 Δd，精度提升到二阶，走圆弧/大角度转弯时误差明显更小。
Q20里程计的误差来源有哪些？
分系统性误差和随机误差。系统性：轮径/轮距标定不准、编码器量化；随机性：打滑、地面不平、转弯时两轮路径差异。系统性靠标定消除，随机性要靠融合 IMU / 激光 / 视觉来抑制。
Q21怎么标定轮径和轮距？
用"已知真值"反推参数。走一段已知长度的直线（如 1m），用实测里程反推轮径系数；原地转一整圈（360°），用实测角度反推轮距。本工程的 ODOM_WHEEL_R_M / ODOM_COUNT_PER_REV / ODOM_WHEEL_BASE_M 目前是占位值（[CO_application.c:39-48](file:///home/zcy/Project/panasonic_canopen_agv/CO_application.c#L39-L48)），需实测替换。
Q22CiA402 是什么？
CANopen 的驱动器/运动控制行规。它定义了驱动器状态机（控制字 0x6040 / 状态字 0x6041）和运动相关 OD（0x6064 实际位置、0x60FF 目标速度等）。本工程用的步进一体机就是 CiA402 从站。
Q23既然有 0x6064，为什么还要自定义 0x6FFF 放位姿？
因为 0x6064 只是"轮子转了多少"，不是"车在哪"。0x6064 是单电机原始计数，不含车体几何。要得到车在世界坐标的 x,y,θ，必须用差速运动学把两轮合成（第 7 站），所以自定义了 0x6FFF 三元素数组来承载结果。

§4 上位机与网络通信

Q24CiA 309-3 ASCII 网关是什么？
一个把"文本命令"翻译成 SDO/NMT 的模块。它内置于 CANopenNode，PC 通过 TCP（或 stdio / 本地文件）发一行文本如 [seq] 1 r 0x6FFF 1 r32，网关替你发 SDO 读，再把结果格式化成 [seq] <value> 返回。这样 PC 不用自己写 CANopen 主站。
Q25为什么用网关，而不自己在板子上写个 TCP 服务？
因为网关板端已内置，零新增协议代码。只要给 canopend 加一个 -c "tcp-60000" 参数就打开了。自己写 TCP 服务要维护报文格式、解析、并发，只有需要"高频主动上报"时才值得。
Q26Qt 上位机为什么要分线程？
因为 socket 的 read() 会阻塞，会卡死界面。做法是"工作线程收发数据 + 用信号槽把结果投递回 UI 线程"：QThread + moveToThread，跨线程用队列连接，无需手写锁。通信全在 CommWorker，界面只更新显示。
Q27Qt 信号槽跨线程安全吗？
安全。跨线程 emit 默认走队列连接：参数被拷贝、投递到接收者线程的事件循环里执行，等于自动串行化，天然避免了数据竞争。前提是参数类型可拷贝（或已注册）。
Q28轮询（SDO）和主动上报（PDO）怎么取舍？
轮询简单可控，上报实时性好。轮询实现容易、时序清晰，但延迟约等于轮询周期、且占带宽；PDO 主动上报延迟低，但需配映射、还要处理丢帧。本工程先用 SDO 轮询（3 个子索引 × 100ms ≈ 300ms 一轮），够看轨迹用。
Q29网关响应怎么区分"成功 / 值 / 错误"？
看 [seq] 后面跟什么。写或 NMT 成功 → [seq] OK；读成功 → [seq] <value>；失败 → [seq] ERROR:0x........ #说明。客户端靠序号 seq 把响应和请求对上（本工程 Qt 里用 seq→subindex 映射还原）。
Q30上位机断线了怎么处理？
检测 + 重连 + 超时保护。监听 socket 的 error/disconnected 信号，做自动重连；板端网关也可设 -T <ms> socket 超时，长时间无数据就断开，避免连接僵死占用资源。

§5 项目综合与工程取舍

Q31你这个项目整体做了什么？
一个基于 CANopen 的差速 AGV 从站 + 上位机。在松下 AGV 工程基础上：双电机差速驱动（双 OD）、里程计位姿估计、自定义 OD 条目 0x6FFF 暴露位姿、CiA309 网关对外提供文本接口、Qt 上位机实时显示轨迹。技术栈：CANopenNode V4 + SocketCAN + i.MX6ULL + Qt。
Q32 ★两个电机，你怎么用一个 canopend 进程管？
用 CO_MULTIPLE_OD 开双实例。编译加 -DCO_MULTIPLE_OD，进程里建两个 CO_t：CO 挂 OD（右电机）、CO_2nd 挂 OD_2nd（左电机），共用同一根 can0，靠节点号区分彼此。
Q33 ★加自定义 OD 条目时踩过什么坑？
两个：索引顺序，和条目第二字段。① ODList[] 必须按 index 升序，因为 OD_find 是二分查找——所以自定义条目索选取 0x6FFF（大于所有既有索引，天然排最后），纯追加即可。② 条目第二字段（子索引总数）规则是 = 数组元素数 + 1（含 sub0）：3 元素数组应填 0x04。填错会返回 ERROR:0x06090011 #Sub index does not exist.
Q34如果让你继续优化，你会做什么？
四点：降延迟、加健壮性、量化精度、做闭环。① 位姿改 TPDO 主动上报降低延迟；② 加心跳 0x1017 + EMCY 0x1014 做在线/故障监测；③ 做里程计标定 + 误差量化（出误差表）；④ 上位机下发运动指令做直线/圆弧/航迹跟踪闭环。
Q35为什么用现成协议栈，而不是自己从零写？
站在成熟栈上，聚焦"集成与链路"。CANopenNode 已实现协议、状态机、网关，自己重写等于重复造轮子且更易出错。工程上更省时可靠，也让我能把精力放在真正的难点：多实例、跨线程取数、自定义 OD、上位机联调。
