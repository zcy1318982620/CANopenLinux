C++ 知识 1-①　argc / argv 到底是什么

在终端敲 ./MusicPlayerWW -hide，操作系统交给 main 的就是这两个参数：

  • argc = 2（./MusicPlayerWW 算一个，-hide 算一个）
  • argv[0] = "./MusicPlayerWW"，argv[1] = "-hide"，argv[2] = nullptr（数组结尾一定是空指针，这是可以在不知道 argc 时遍历的保证）

每个元素都是 char*（C 风格字符串），本质是「以 '\0' 结尾的一串字节」。所以 不能用 == 比较内容（那比的是地址），C 里要用 strcmp()。本项目偷了个懒：把它交给 QString 去比，所以写法很干净。

关键点：参数是「运行时才给」的，程序无法在编译期知道有几个参数。所以任何用到 argv[n] 的地方，前面必须有一个 argc 范围的检查 —— 本项目 :9 和 :10 就是这两道闸门。

C++ 知识 1-②　运算符重载：为什么 argv[1] == QStringLiteral("-hide") 能比较字符串

QStringLiteral("-hide") 是一个宏，编译期就把字面量转成 QString 对象（比运行时 QString("-hide") 快，因为它不用每次去算长度和做编码转换）。

于是 argv[1] == QStringLiteral("-hide") 里，右边已经是个 QString。C++ 看到「const char* 和 QString 用 ==」，会先做隐式类型转换把左边也变成 QString（QString 有接受 const char* 的构造函数，且没标记 explicit），然后调用重载过的 QString::operator==，做的是内容逐字符比较。

一句话记住：「== 比的是地址」只对裸指针成立；一旦某一侧是类类型，== 就可能被重载成"按内容比"。这也是 C++ 和 C 的一个哲学差异。

坑 1-①　条件顺序不能反。如果把 :10 写成 if(argv[1] == QStringLiteral("-hide") && argc >= 2) —— 不带参数运行时 argv[1] 是 nullptr，用 QString 接 nullptr 虽然不会立刻崩，但语义已经是「用了不存在的参数」。这就是典型的越界/空指针问题，必须靠「先判长度、再取值」的顺序躲开。

为什么要支持 -hide 启动？因为主菜单进程是用 QProcess::start(路径, QStringList("-hide")) 把它拉起来的（见上一篇 §2）。主菜单在程序一启动时就把播放器进程挂在后台，但这时候用户还在看主菜单，播放器窗口不能弹出来。所以约定：主菜单拉起的就用 -hide 静默启动，用户双击的就不带参数正常显示。一个 if 解决了两种启动场景。

C++ 知识 2-①　初始化列表 vs 构造函数体赋值

对比下面两种写法：

// 写法 A：初始化列表（本项目用的）
MainWidget::MainWidget(QWidget *parent) : QWidget(parent), ui(new Ui::MainWidget)
{
    ui->setupUi(this);
}

// 写法 B：函数体里赋值
MainWidget::MainWidget(QWidget *parent) : QWidget(parent)
{
    ui = new Ui::MainWidget;   // 合法，但不推荐
    ui->setupUi(this);
}

区别有三条：

  • 顺序：成员永远按「声明顺序」初始化，且一定在函数体之前完成。用列表能让你看清真实顺序。
  • 能不能：const 成员、引用成员、没有默认构造函数的类成员，只能用初始化列表赋值。
  • 效率：写法 B 对类成员相当于「先默认构造一次，再赋值一次」；int 这类内置类型在写法 B 里则是先随机值、后覆盖。

易错点：很多人以为成员是按「列表里写的顺序」初始化的，于是写下 : b(a), a(1)，结果 b 拿到的是未初始化的 a —— 因为实际顺序是声明顺序 a 再 b。编 -Wall 时会报警告。

C++ 知识 2-②　new Ui::MainWidget 是什么，为什么要 delete

Ui::MainWidget 不是本项目手写的类，而是 uic 工具根据 MainWidget.ui 自动生成的（生成文件 ui_MainWidget.h）。它的内容大致长这样：

namespace Ui {
class MainWidget {                      // 纯 C++ 类，不是 QObject！
public:
    QPushButton *btnPlay;               // 界面上每个控件一个裸指针成员
    QSlider     *sliderProgress;
    ...
    void setupUi(QWidget *MainWidget);  // 按 .ui 把控件建出来
};
}

要点：它没有继承 QObject，所以它不在 Qt 对象树里、不会自动被回收；但它持有一堆 `new 出来的控件指针` —— 那些控件挂到了 this（主窗口）名下，主窗口销毁时它们会一起没。于是真正该手动 delete 的，就只剩这个「装指针的小盒子」本身：这就是 :49 delete ui; 的全部意义。

因果链：主窗口析构 → 先执行 ~MainWidget() 里的 delete ui（释放盒子）→ 再执行 QWidget 的析构（对象树递归删掉所有子控件）。顺序反了也不会立刻崩，但概念上要清楚：盒子先走，控件后走。

坑 2-①　全局变量不宜多用。:18-20 这四个全局变量谁都能改（本项目 MainWidget.cpp 里就有多处直接写 volRecord = …），排查问题时「谁把它改了」很难找；而且不同 .cpp 里的全局变量初始化顺序不保证。更好的做法是把它们收进类里当成员，或放到一个专门的「设置」类里。

:32-34 和 :36-44 为什么被注释掉了？这是作者留下的「自动扫描音乐」功能（scan_music()、add_music_to_list()、init_playlist() 三个函数在 :290-312、:407-414 定义着，但没被调用）。现在改成了「手动添加 + SQLite 记住歌单」的方案。读到没被调用的函数，不要以为漏了什么 —— 全篇末尾的 §13.3 会统一盘点这类「死代码」。

C++ 知识 3-②　inline 与「头文件里的函数定义」

正常规则是「函数定义放 .cpp，声明放 .h」。如果把函数定义直接写进头文件，而这个头文件被多个 .cpp #include，那么链接时就会出现「同一个函数被定义了好几次」的重复定义错误。

inline 就是给编译器的许可：「这个函数可以有多个完全相同的副本，随便挑一个用」。于是头文件里的小函数可以用 inline 安全地定义。本项目 7 个 QSS 函数全是 #include "MyQSS.h" 直接调用的，就靠这个 inline 生效。

补充：类成员函数如果写在类定义内部（如 MyMusic.h:27 的 QUrl get_url() const {return url;}），会自动具备 inline 性质，不用手写。这就是为什么 MyQSS.h 里必须显式写、而类内函数不用写。

为什么不直接用 .qss 文件？用文件就要处理「文件路径找不到」「编译时不会报错」等问题；写成 inline 函数，编译期就能检查、还能带参数（本项目的 ScrollBarStyle() 就带了颜色等常量）。代价是改样式要重新编译。两者各有场景，小项目用函数更顺手。

C++ 知识 4-①　成员函数指针：&QMediaPlayer::stateChanged 是什么

&QMediaPlayer::stateChanged 取的不是某个对象的成员，而是「这个信号在类里是第几个成员」这种「类级别的地址」。C++ 里叫「成员指针」（pointer to member）。它不能单独调用，必须配一个对象：

void (QMediaPlayer::*p)() = &QMediaPlayer::stop;   // 类的成员函数指针
QMediaPlayer player;
(player.*p)();                                      // 配上对象才可调用（.* 运算符）

Qt5 的 connect 新语法正是利用这个特性：信号和槽的类型在编译期就能被检查，参数不匹配直接编译报错。对比 Qt4 的字符串写法 connect(player, SIGNAL(stateChanged(QMediaPlayer::State)), ...) —— 写错了要等到运行时才在终端打印警告，程序却不崩，非常难查。

为什么传的是「基类的信号」？例如 &QAbstractSlider::valueChanged：QSlider 自己没重定义这个信号，它继承自 QAbstractSlider。C++ 允许用「基类名」来指代继承来的成员，所以这么写完全合法。

C++ 知识 4-②　枚举（enum）与作用域

本项目里到处出现 QMediaPlayer::PlayingState 这种「类名::值」的写法，原因是 C++ 的普通枚举值会泄漏到外层作用域：

enum State { StoppedState, PlayingState, PausedState };   // 传统 C 风格 enum
// 直接用 PlayingState 也行，但很容易和别处的同名值冲突
player->state() == QMediaPlayer::PlayingState             // 本项目这种写法更清楚、也避免冲突

坑 4-①　playlist 没有父对象，也没被 delete。:74 playlist = new QMediaPlaylist; 后面再也找不到 delete playlist（析构函数 :47-50 只删了 ui）。所以这个对象会一直活到进程结束，属于内存泄漏。本进程整个生命周期只 new 一次，泄漏量很小，但习惯不对。

C++ 知识 5-①　RAII：栈对象自动析构

注意 :88 QSqlDatabase database; 和 :112 QSqlQuery querySql; 都是在栈上直接定义对象，没有 new，也没有 delete。函数一返回，它们就自动析构。这个「把资源的释放交给析构函数」的做法有个专门名字：RAII（Resource Acquisition Is Initialization，资源获取即初始化）。

本项目里到处都是 RAII 的影子：

  • MyMusic.cpp:29 QMediaPlayer tmpPlayer; —— 临时播放器，用完自动销毁。
  • LyricWidget.cpp:26 QFile lyricFile(filePath); —— 文件对象，出作用域自动关文件。
  • MusicList.cpp:19 QProgressDialog proDialog(...); —— 进度对话框，函数结束自动消失。
  • main.cpp:8 MainWidget w; —— 主窗口也一样。

对比 new：new 出来的对象必须有人负责 delete（要么你自己，要么 Qt 父子关系）。能用栈对象就别用 new，这是 C++ 最重要的一条经验。

C++ 知识 5-②　QVariant：Qt 的「万能类型」

querySql.value(0).toInt() 里的 value(0) 返回的是 QVariant —— 一个能装下 int/double/QString/QImage… 任意类型的「盒子」。SQL 的列类型在运行时才知道，所以必须有个万能盒子来装。

用法就三步：存（构造函数或 QVariant::fromValue）、取（toInt()/toString()/toLongLong()）、强类型取（value<QImage>() 模板函数）。本项目 :266 就是这么拿封面的：

坑 7-②　每秒硬轮询 + attach/detach 当探针，既不优雅也不好查错

① readTimer->start(1000) 意味着每条命令平均要等半秒才被执行 —— 按一下音量键，要愣一下才响应。② qDebug() << "等待" 在没命令时也每秒打一行，串口/终端会被刷屏，真出问题时反而看不见有用日志。③ 用「attach 成功与否」当「有没有新命令」的探针是很脆弱的：只要对端 create 过又没销毁，attach 就一直成功，可能反复执行同一条旧命令。

更正规的做法：① 用真正的事件通知（QLocalSocket/QLocalServer 或 D-Bus），有数据才醒，不用轮询；② 共享内存方案里，读方读完后主动把值清 0（本项目 shm_to_zero() 就是在干这件事），并配合 QSystemSemaphore 做真正的同步，而不是靠 attach 的成败。

为什么不干脆用「一个进程 + 多个窗口」？因为作者想让播放器独立可执行（MusicPlayerWW 能单独双击运行调试），又想被主菜单「收养」。于是用 QProcess 拉起 + -hide 参数控制初始可见性（§1），再用共享内存代替「函数调用」。代价：两个进程的通信协议（六个宏的值）必须严格一致 —— 改了一边忘了另一边，就会出现「点了没反应」这种极难查的 bug。所以宏定义在两个工程的 MainWidget.h 里各写了一份，务必同步修改。

C++ 知识 8-①　switch 语句：本质是一张「跳转表」

switch(num) 先算出 num 的值，再直接跳到匹配的 case 标签处 —— 它不是一串 if-else 依次比较，而是编译成「跳转表」，所以分支很多时比 if-else 快。三条铁律：

  • ① case 后面必须是「编译期常量」：整数或枚举。不能是变量、float、QString。本项目用的 SWITCH_VISIBILITY 等宏，预处理后就是常量 1..6，合法。
  • ② break 不能忘：忘了 break，程序会「贯穿」到下一个 case 继续执行（fallthrough）。本项目每个分支都规规矩矩写了 break。偶尔「故意贯穿」是有用的技巧，但要加注释说明，否则会被当成 bug。
  • ③ default 兜底：所有 case 都不匹配时执行。本项目写成「空 + break」，即「不认识的命令就忽略」，这是最稳妥的默认策略。

对比 if-else：if 擅长范围判断（x > 20 && x < 60），switch 擅长「一堆离散等值」。用错场景不会报错，但可读性和性能都差。

坑 8-①　VOL_UP 和 VOL_DOWN 逻辑不对称，音量行为很怪

看这两行（MainWidget.cpp:164 与 :168-169）：

case VOL_UP:                                   // 音量增大
    ui->sliderVol->setValue(volRecord);        // 直接把滑块设成「记忆值」
    break;

case VOL_DOWN:                                 // 音量减小
    if(ui->sliderVol->value() > 20) ui->sliderVol->setValue(20);  // 只允许降到 20？
    volRecord = ui->sliderVol->value();
    break;

问题：① VOL_UP 是「恢复记忆音量」，根本不是「在当前基础上 +1」；② VOL_DOWN 更奇怪 —— 当前音量大于 20 就直接跳到 20，小于等于 20 就什么都不做，这不是「减小」，是「设上限」。③ 两者的行为完全不对称（一个用 volRecord，一个不用），说明这段逻辑是没写完/写错的占位代码。

正确写法应是对称的步进，例如：

case VOL_UP:   ui->sliderVol->setValue(ui->sliderVol->value() + 5); break;
case VOL_DOWN: ui->sliderVol->setValue(ui->sliderVol->value() - 5); break;
//（setValue 内部会自动裁剪到 sliderVol 的 [minimum, maximum] 范围）

为什么读完后要 shm_to_zero()？因为共享内存不会自己「消费掉」数据。如果不清零，下一次 readTimer 的 attach() 仍会成功、仍读到同一个旧数字，于是同一条命令被无限重复执行（比如 CLOSE_APP 会一直触发 close()）。shm_to_zero() 就是「把信箱掏空」的手工确认机制 —— 属于「手动 ACK」，这是很多嵌入式进程通信里常见的土办法：能跑，但要靠人守规矩。

坑 9-①　内置类型成员不初始化 = 垃圾值（本项目的定时炸弹）

看 MyMusic.h:23：MyMusic() {} —— 空函数体，什么都没做。而 duration（qint64）、bitRate（int）是内置类型（不是 QString/QImage 这种有构造函数的类）。C++ 规则是：

  • QString title; → 会调用 QString 的默认构造，得到一个空字符串（安全）。
  • qint64 duration; → 什么都不做，值是「这块内存里原来是什么就是什么」，也就是随机垃圾值。

本项目为什么没炸？因为 MusicList::read_from_sql() 里（MusicList.cpp:119-125）创建 MyMusic tempMusic; 之后立刻把 6 个字段全部赋了值，所以垃圾值马上被覆盖。但这是「靠后面的代码自觉」—— 只要哪天有人

qDebug() << my_format_time(m.duration);     // ✗ 用垃圾值算时间，输出莫名其妙

就会得到一个看不懂的乱码时长。正确写法（二选一）：

qint64 duration = 0;     // 方案 A：类内默认值（C++11 NSDMI）
int    bitRate   = 0;
// 或者 方案 B：
MyMusic() : duration(0), bitRate(0) {}   // 放进初始化列表

坑 9-②　init_from_url() 里的忙等：一整颗 CPU 核在空转

// MyMusic.cpp:29-32

// 元数据的解析需要时间，所以这里需要循环等待

setMedia 是异步的：它交完任务就立刻返回，元数据要等底层解码器读出来才可用。作者用了一个「忙等（busy wait）」：不停问 isMetaDataAvailable()，没好就 processEvents() 转一圈事件循环再问。

C++ 知识 9-④　运算符重载与「仿函数」（函数对象）

operator() 是 C++ 允许重载的运算符之一，意思是「让这个对象也能像函数一样被调用」：

MusicCompare cmp(DURATION);      // 造一个「按 DURATION 比」的尺子

这种「长得像函数、其实是对象」的东西叫 仿函数 / 函数对象。它比普通函数强的地方在于：能带状态。本项目 key 就是状态 —— 同一把尺子，换个 key 就变成「按歌名比」或「按时长比」，一份代码不用写三个函数，这正是 sort_by(COMPARE key) 能用一个参数切换排序方式的原理。

和 lambda 的关系（呼应 §7 蓝框 7-①）：lambda [&](const MyMusic&A, const MyMusic&B){...} 本质上就是编译器替你生成的一个类似的仿函数类。能写 lambda 的地方就能手写仿函数，反之亦然：

// 用 lambda 实现「按 DURATION 降序」，可以不写 MusicCompare 类：
sort(musicArr.begin(), musicArr.end(),
     [](const MyMusic&A, const MyMusic&B){ return A.duration > B.duration; });

另外看 enum COMPARE{DEFAULT, TITLE, ...}：这叫传统 enum，它的名字会「泄漏」到外层作用域（TITLE 这个符号在整个 MyMusic.h 后面都能直接用，不需要写 COMPARE::TITLE）。现代 C++ 推荐 enum class COMPARE { Default, Title, ... };，必须写 COMPARE::Title，不会污染，也不允许随便跟 int 混算（对比 §4 蓝框 4-②）。

C++ 知识 9-⑤　迭代器与 auto：容器的「通用游标」

数组用下标 a[i]，但链表没有下标，只能在节点间「走」。为了让所有容器都能用同一套遍历代码，STL 抽象出迭代器 —— 一个「类指针」的东西：

for(auto i = musicArr.begin(); i != musicArr.end(); i++)
{                        //  ↑ 让编译器自动推导类型（就是 vector<MyMusic>::iterator）
    i->get_url();        // ✗ 用「箭头」：i 像指针一样被解引用
    (*i).get_url();      // ✓ 完全等价
}

三个必须记住的点：

  • ① end() 指向「最后一个元素的后面」，所以循环条件是 != end() 而不是 < end()（虽然 vector 恰好能用 <，但链表迭代器不支持比较大小）。
  • ② auto 是「类型自动推导」（C++11），不是「动态类型」。它写起来省事，编译后跟手写完整类型完全一样，零性能开销。
  • ③ 迭代器会「失效」：push_back 触发扩容、或 erase 之后，之前的迭代器全部作废，继续用就是野指针。本项目在 add_music 里边 push_back 边用 [size()-1] 而不是迭代器，恰好躲过了这个坑。

Qt 的 QList/QVector 也提供同样的 begin/end，还有更方便的 foreach 宏（本项目 MusicList.cpp:25、:63 用了它）。foreach 是拷贝遍历，处理自定义类型时最好写 const MyMusic &i 避免拷贝（本项目 :63 写对了，:25 的 QUrl i 是拷贝但 QUrl 很轻，无妨）。

MusicList.h:7 写了一句 using namespace std;。它让这个头文件后面 vector、sort、string 不用写 std::，看着省事。但 #include 是文本插入 —— 任何包含了 MusicList.h 的 .cpp 文件，都会被迫进入 std 命名空间：

// 假设你写了这样一个函数名：

C++ 知识 9-⑦　sort / unique / 仿函数，以及 erase-remove 惯用法

① std::sort（<algorithm>）：把 [first, last) 排成「升序」。第三个参数是「小于比较器」—— 传 MusicCompare(key)，就按 key 指定的字段排。★ 两点：

  • 比较器必须满足「严格弱序」：即不能用 <= 当「小于」，必须用 <。写成 A.duration <= B.duration 会让排序行为错乱甚至崩溃。
  • sort 是不稳定排序（相等元素的前后顺序可能被打乱）。要保证稳定用 stable_sort。

② std::unique 的一半真相：它不删除元素！它只把「相邻的」重复元素往后挪，返回「新的逻辑结尾」：

[1,1,2,2,2,3]  ──unique──>  [1,2,3,?,?,?]
                              ↑ 返回这里   ↑ 后面是「待清理的垃圾」

所以必须先排序（让重复的挤到一起），再用 erase-remove 惯用法把尾巴剪掉：v.erase(unique(v.begin(), v.end()), v.end())。本项目 :84-86 正是这个套路，写得很标准。

③ 完整对照：

算法功能前提 / 返回值
sort(b,e,cmp)升序排列不要求有序；无返回
stable_sort稳定排序相等元素保持原相对顺序
unique(b,e,pred)把「相邻重复」挪到尾部★ 必须先排序；返回新结尾迭代器
find / count / max_element查找 / 计数 / 求最大同样吃迭代器区间，本项目未用

坑 9-④　去重用的判据和排序用的判据不一致

neaten() 里：排序用 MusicCompare(DEFAULT)，即按 get_brief_info()（歌手 + 歌名 + 时长）去重用 MusicCompare(EQUALITY)，即按 url 判等。而 unique 只能删相邻的重复项，所以「靠 url 判出来的重复」必须恰好也是「相邻的」才行。

目前侥幸成立，因为同一个 url 解析出来的歌手/歌名/时长必然相同，所以同 url 的两条记录在 brief_info 上必然相等、排序后必然相邻。但这是一个隐含的巧合：只要 get_brief_info() 以后改成包含 bitRate、或加入「播放次数」，同 url 记录就可能不再相邻，去重会悄悄漏掉。更稳的写法是两个判据一致 —— 排序也用 EQUALITY 对应的字段（url）。

坑 9-⑤　remove_sql_all() + insert_sql_all()：每次排序都「全表删除重建」

sort_by/neaten/clear 之后都是「把数据库里的歌全部删掉，再把内存里的 vector 全部重新插一遍」（:78-79、:86-88、:93）。三个问题：① 慢：几百首歌就是几百条 INSERT，且每条都重新 prepare；② 中途崩溃就丢数据：删除已经提交、插入还没完，程序一挂歌单就空了；③ 顺序本来只是「显示顺序」，完全可以只改内存、加一个 order 字段存序号，不必整表重写。

正确做法：用事务把删除和插入包起来（db.transaction() / commit() / rollback()），要么全成功要么全回滚；或者干脆不在排序时动数据库。

C++ 知识 12-①　connect() 写在槽函数里，会发生什么？

一般写法是把 connect 放在构造函数（或 init_*()）里，整个对象生命周期只执行一次。而这里 :355 的 connect 写在 on_btnQuit_clicked() 里 —— 每点一次「退出」，就多建立一条同样的连接。

于是第 N 次点退出后，detachTimer 超时一次会回调 N 次 lambda：第一次已经 detach()，后面几次对一个「没有 attach 的 QSharedMemory」再 detach()，会打印 QSharedMemory::detach: not attached 之类的警告。

Qt 提供了一个开关来防这件事：

connect(detachTimer, &QTimer::timeout, this, [&](){ ... },
        Qt::UniqueConnection);   // 同名同类型的连接只保留一条

但 Qt::UniqueConnection 对 lambda 形式的连接是无效的（因为每次写的 lambda 类型都不同，Qt 没法判定「这是同一条」）。所以正解是：把连接建到构造函数 / init_shm() 里，只建一次。这是「在哪初始化，就在哪连接」的原则。

顺带一个 C++ 细节：lambda [&](){ ... } 本身是一个匿名类的临时对象（闭包），connect 会把它的副本存进内部的连接记录里。所以只要这条连接还在（detachTimer 还活着），这个闭包副本就活着 —— 这就是「lambda 的寿命由连接决定」，也正是 §7 坑 7-① 里 [&] 悬垂问题的另一半真相：引用捕获 + 长命连接 = 悬垂引用。

C++ 知识 12-②　new 出来的对象，到底谁来 delete？

C++ 里没有垃圾回收，new 必须配对 delete。Qt 给了一个省事的替代品：父子对象树（parent-child）。规则是：

QTimer* t = new QTimer(this);   // 传了 this 当 parent
// 当 this 被 delete 时，Qt 会自动 delete t —— 不用自己写 delete

所以本项目里 switchAppTimer / readTimer / detachTimer 都带 this，是安全的。但有三类 new 逃过了这棵树的保护：

① playlist = new QMediaPlaylist;（§4 坑 4-①，没传 parent）；
② new QPropertyAnimation(btn, "geometry")（见坑 12-②，第一个参数是「动画目标」，不是 parent！）；
③ 各种 new QListWidgetItem（由 QListWidget 接管所有权，这条其实安全）。

C++ 的标准答案是用智能指针把「谁 delete」写进类型里：

std::unique_ptr<QMediaPlaylist> playlist;   // 离开作用域自动 delete
QScopedPointer<QPropertyAnimation> anim;    // Qt 版，语义同上

一句话记法：new 的时候，要么给 parent，要么交给智能指针，要么自己 delete。三样都没有 = 泄漏。

坑 12-①　connect 写在槽里 → 每点一次「退出」就多连一条。MainWidget.cpp:355 的 connect(detachTimer, &QTimer::timeout, ...) 写在 on_btnQuit_clicked() 函数体内。第一次点没问题；第二次点，detachTimer 上就有两条一模一样的连接，超时会执行两次；第三次点变三条……功能上看不出大问题（重复 detach 只是打警告），但这是典型的「连接越积越多」缺陷，代码评审一定会被指出来。改法：把这段 connect 挪到 init_shm()（或构造函数）里只连一次。

坑 12-②　zoom() 每次点按钮都泄漏一个动画对象。MainWidget.cpp:314-327：

314 void MainWidget::zoom(QPushButton* btn)
315 {
316     QPropertyAnimation* animation = new QPropertyAnimation(btn, "geometry");
317     ...                                              // 设置时长/起止值/曲线
326     animation->start();                              // 启动
327 }                                                    // ← 函数结束，指针丢了，对象还在！

★ QPropertyAnimation(btn, "geometry") 的第一个参数是被动画的对象，第二个参数是属性名，并没有第二个「parent」参数。所以这个 animation 没有被挂到任何父对象上，函数一返回，animation 这个局部指针就没了 —— 对象却还活着，而且没人能再 delete 它。

① 加一行 animation->setParent(btn); —— 让它跟着按钮一起被回收；
② 更推荐：animation->deleteLater(); 或者干脆用 QPropertyAnimation anim(btn, "geometry");（栈对象，函数返回即析构，动画已经 start() 了、Qt 内部会自己接管播放，寿命不受影响）。
