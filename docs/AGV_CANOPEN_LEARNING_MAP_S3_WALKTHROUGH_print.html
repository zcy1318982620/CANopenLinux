第 3 站 · 对象字典 OD 与 SDO —— 参数存在哪、怎么读写

工程：panasonic_canopen_agv —— 松下「実験用 AGV」双轮差速底盘，基于 CANopenNode V4 的 CANopen 从站（Linux 用户态 + SocketCAN，进程名 canopend）。双对象字典：OD（右电机）/ OD_2nd（左电机）。

0. 一页地图：第 3 站只有两条链

先给一句话结论：OD 是「节点身上有什么数据、放在哪、能不能读写」；SDO 是「网络上别人怎么按索引来读写这些数据」。前者是静态的仓库，后者是动态的搬运工。

第 3 站 全部内容

链 A  对象字典 OD —— 节点自己身上的「数据总目录」（静态，开机就存在）
   索引       目录表 ODList[]        描述符 ODObjs          数据区(变量)
  0x6064  ──▶ [ 索引 0x6064 那一行 ] ──▶ [ 0x6064 的「名片」 ] ──▶ 真正的值

   一句话：输入一个「索引」，能一路走到「值」。

链 B  SDO —— 网络上「点对点」读写这些数据（动态，收到帧才动）
   请求帧 ─▶ CO_SDO_receive() ─▶ CO_SDOserver_process()

                                       ├─ 落地：io.read() / io.write()

   一句话：SDO 就是「拿链 A 的机制，替远端的客户端读/写一条 OD」。

   ★ 本项目还在 0x6064 上挂了一个「应用钩子」：
       别人一写 0x6064 → 不落默认内存，而是调用 H6064_write() → 打印 posR / posL
为什么这两件事要放一站讲？SDO 本身不存数据，它只做「翻译」：把线上的请求翻译成「对 OD 某一行的一次读/写」。所以 OD 是内容，SDO 是通道。不先讲清 OD，SDO 就只是空中楼阁；不接着讲 SDO，OD 就只是躺在内存里的一堆常量。

1. OD 是什么：CANopen 的「数据总目录」

1.1 一句话原理

CANopen 有一条核心设计：总线上不传变量名，只传地址。这个地址就是「索引 + 子索引」。每个节点把自己的全部可访问数据编成一张表，表里每一项都用一个「索引:子索引」当门牌号——这张表就叫对象字典（Object Dictionary, OD）。

所以任何一次通信（不管是第 4 站的 PDO，还是本站的 SDO），第一步都要落到某个 index:sub 上，协议栈才知道「读谁 / 写谁」。这不是本项目的设计，是 CANopen 协议规定死的。

1.2 一个「对象」由 4 件事定义

表 1-1　OD 里每一项都能用这 4 件事描述清楚
要素含义
索引 Index
（16 bit）		0x0000–0xFFFF。协议划了区：0x1000–0x1FFF = 通信参数（NMT/心跳/SDO/PDO 的配置都在这）；0x2000–0x5FFF = 厂商自定义；0x6000–0x9FFF = 设备行规，CiA402（伺服驱动）就在这里，如 0x6041 状态字、0x6064 实际位置。
子索引 SubIndex
（8 bit）		一个索引下可以有多个成员，用子索引区分。例如 0x1018（设备身份）下有 4 个成员：厂商 ID、产品码…
数据类型如 UINT32、INTEGER32、BOOLEAN、VISIBLE_STRING。决定这个值占几个字节、怎么解释。
访问权限只读 / 只写 / 读写，外加「能不能被 SDO 访问」「能不能被 PDO 传输」。权限不够时读写会被拒（转成 abort，见 §4）。

2. 链 A 的骨架：OD 的三张表

打开 application/OD.c，会发现它其实是三块数据 + 最后一句组装。下面按「它到底存了什么」来拆。

表 2-1　OD.c 里的三块数据
块是什么在本项目里的样子
① 数据区
（值存在这）		两个 C 结构体，字段就是各对象的当前值。OD_PERSIST_COMM=掉电要保存的（如心跳周期、PDO 配置）；OD_RAM=掉电不留的（如状态字、实际位置）。OD_RAM.x6064_positionActualValue 就是「实际位置」这个值本身。
② 描述符表

三块拼完，文件最后一句把「目录」变成一个可用的 OD 对象：

文件：application/OD.c（第 2121–2126 行）
 static OD_t _OD = { (sizeof(ODList)/sizeof(ODList[0])) - 1,   /* size = 对象个数 */
                     &ODList[0] };                             /* list = 目录首地址 */
 OD_t *OD = &_OD;                                             /* 全局指针 OD ★★★ */

就地说明：OD_t 就两个字段——size（这本字典有多少项）和 list（目录首地址）。算出来的 size = 157，说明目录里 list[0..156] 是 157 个真对象，第 157 行是哨兵。OD 是个全局指针，全工程（协议栈、应用）都通过它访问右电机字典；左电机对应的是 OD_2nd。

2.1 从「索引」走到「值」：链 A 的核心流程图

有人想访问 0x6064
   │
   ▼
① OD_find(OD, 0x6064)
   │   干什么：在目录表 ODList[] 里按索引找「那一行」
   │   怎么找：因为目录已按索引升序排列 → 可以「二分查找」，不用从头翻
   │   返回：OD_entry_t*（目录行的指针）；找不到 = NULL
   ▼
② 拿到这一行后：OD_getSub(entry, subIndex=0, &io, odOrig=false)
   │   干什么：把「目录行 + 子索引」翻译成「这条数据怎么读、怎么写」
   │   结果填在 io 里：io.read / io.write 两个函数指针 + 一条 OD_stream_t
   │        （OD_stream_t 里记着：值在哪(dataOrig)、多长(dataLength)、什么权限(attribute)）
   │   返回：ODR_t（ODR_OK=成功；否则是具体错误，如「对象不存在」「没有这个子索引」）
   ▼
③ io.read() 或 io.write()
   │   干什么：真正把数据搬进/搬出内存
   ▼
④ 数据区的真值：OD_RAM.x6064_positionActualValue
为什么要拆成三张表、还非得排序？三个理由：① 好自动生成——EDS 变了，工具重新生成一次 OD.c 即可；② 值与描述分离——值在可写的 RAM，描述是常量，放只读区更省更安全；③ 能二分查找——目录有序，157 个对象最多比 8 次就能定位（这决定了 OD_find 的实现方式）。这三件事合起来，就是整个 OD 模块存在的意义。

3.1 OD_find + OD_getSub：一对「查表搭档」

这两个是整个 OD 的入口，几乎所有访问都要先过它们。分工很清晰：OD_find 管「按索引找到那一行」，OD_getSub 管「这一行里的第几个成员怎么读/写」。

OD_find(od, index)                 OD_getSub(entry, sub, &io, odOrig)
 ─ 输入：哪本字典 + 索引              ─ 输入：目录行 + 子索引
 ─ 动作：二分查找 ODList[]            ─ 动作：看这一行是 VAR/ARR/REC，分别算：
 ─ 输出：目录行 或 NULL                     VAR → sub 必须=0，取名片里的地址/长度
                                         ARR → sub0=个数，subN 地址=首地址+元素大小×(N-1)
                                         REC → 在成员表里挨个找 subIndex 相同的那项
                                     ─ 输出：io.read / io.write + 一条 stream（值在哪、多长、权限）

就地说明两个关键结构：

表 3-2　OD_entry_t（目录行）与 OD_stream_t（数据流）

4. 链 B 是什么：SDO（点对点参数通道）

4.1 一句话原理

SDO = Service Data Object，点对点、一问一答的参数通道。它不参与周期性数据传输，专门用来「偶尔读个参数 / 改个参数」。特点：慢，但万能——OD 里任何一个对象它都能读写。

表 4-1　SDO 的四个关键点

谁跟谁说话客户端 ↔ 服务端客户端（一般是主站/配置工具）发起，服务端（从站）应答。本项目作为从站，提供 SDO server；同时内置 SDO client，供命令行当网关用（§6）。

0x06010002对象只读，不能写你硬要写它
0x06020000对象不存在索引写错了
坑：别把 SDO 和 PDO 搞混。SDO = 「配置/调试用的一问一答」，慢但什么都能读写；PDO = 「运行时周期广播」，快但只能传预先映射好的那几个量。本项目运行时把左右轮的实际位置（posR/posL）走 PDO；而要改参数、看参数就走 SDO。第 4 站讲 PDO。
一个把两站串起来的点：PDO 的「配置」（映射了哪几个对象、COB-ID 是多少）本身就存在 OD 里（就是 0x1400/0x1600 这些对象）。而这些配置对象只能通过 SDO 写。所以一句话：SDO 是配置通道，PDO 是数据通道。

5. 链 B 的主链：SDO server 怎么处理一条请求

先讲模块职责：SDO server = 本节点开的一个「参数服务窗口」，替远端客户端读写自己的 OD。它自己不存数据，全部动作都是「查 OD → 读写 → 应答」。

6. 反向：本机当客户端 —— 用命令行读写 OD

本工程除了「被动当服务端」，还能「主动当客户端」：它内置了 SDO client，并配了一个 ASCII 命令界面（网关，CiA 309-3）。这意味着一件很爽的事——不用写一行代码，就能在命令行里读/写任意 OD 对象。

6.1 怎么开、怎么用

启动（多一个 -c "stdio" 就打开命令行网关）：
    ./canopend can0 -i 1 -c "stdio"
    > help                            ← 看全部命令
    > r 0x1017 0                      ← 读 0x1017（心跳周期）的 sub0
    > w 0x1017 0 u16 1000             ← 写 1000（单位 ms）进去
    > 1 write 0x1010 1 vs save        ← 把参数存进保存区（掉电不丢）

关机壳里还有：set node / set sdo_timeout / start / stop / preop / reset node / reset comm / lss_* / log
类型码（写在命令里告诉栈按什么类型解释）：b / i8..i64 / u8..u64 / x8..x64 / r32 / r64 / vs / os / us / d
这是怎么来的？工程根 CO_driver_target.h 里默认打开了 SDO client 与网关（CO_CONFIG_SDO_CLI、CO_CONFIG_GTW 都带 ENABLE/ASCII 标志），所以 Linux 版默认就带这套调试能力。注意别被 CANopenNode/301/CO_config.h 里写的 CO_CONFIG_GTW (0) 误导——那些值是包在 #ifdef CO_DOXYGEN 里的，只给文档生成器看，不参与编译。

7.1 一个「殊途同归」的观察

本项目在 app_programStart()（CO_application.c:65 起）里，用 OD_set_u32 / OD_set_u8 直接改了 OD：

OD_set_u32(OD_ENTRY_H1006_communicationCyclePeriod, 0, 100000, true);  ← SYNC 周期 = 100000 µs = 100 ms
OD_set_u32(OD_ENTRY_H1005_COB_ID_SYNCMessage,      0, 0x40000080, true); ← 使能发送 SYNC
OD_set_u32(OD_ENTRY_H1400_RPDOCommunicationParameter, 1, 0x0000038A, true); ← 右 RPDO 的 COB-ID
OD_set_u8 (OD_ENTRY_H1600_RPDOMappingParameter, 0, 2, true);           ← 映射 2 项
OD_set_u32(OD_ENTRY_H1600_RPDOMappingParameter, 1, 0x60410010, true);  ← 第 1 项：0x6041 状态字，16 bit
OD_set_u32(OD_ENTRY_H1600_RPDOMappingParameter, 2, 0x60640020, true);  ← 第 2 项：0x6064 位置，32 bit

就地说明：OD_ENTRY_H1006… 这类宏就是「第 3 站 §2 里那个目录表的第几行」的现成写法（形如 &OD->list[n]），所以应用不用自己去 OD_find，直接拿宏就能 OD_set。最后那个 true 是「要不要按权限检查」。

关键理解：同样是「配置 SYNC 和 PDO」，有两条路——① 本工程走的是「启动时直接改内存」（OD_set_*，不经过网络）；② 真实主站走的是「用 SDO 写同样的对象」。两条路终点都是 OD 里同一批对象（0x1005/0x1006/0x1400/0x1600…）。看懂这一点，就看懂了 SDO 在整个项目里的角色：它是「把 OD 配置权交给网络另一头」的那条通道。

8. 小结 · 自测 · 站间衔接

8.1 五句话总结

① OD = 节点自己的「数据总目录」，每一项 = 索引+子索引+类型+权限。
② OD.c 是三张表拼的：数据区（值）+ 描述符（名片）+ 目录 ODList[]（按索引有序，可二分）。
③ 访问 OD 靠五件套：OD_find → OD_getSub → io.read/write；出错用 OD_getSDOabCode
   翻译；想拦截就用 OD_extension_init 挂钩子（本工程挂在 0x6064 上）。
④ SDO = 点对点一问一答的参数通道（0x600/0x580），能读写任何 OD 对象；
   server 替别人读我，client 让我去读别人（本项目都有）。
⑤ 运行时数据走 PDO，参数配置/调试走 SDO；而 PDO 的配置本身就存在 OD 里。
