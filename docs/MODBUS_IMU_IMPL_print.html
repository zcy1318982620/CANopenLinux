Modbus RTU IMU 主站实现册：函数职责 + 完整链路

这份文档解决什么：把这次写的 Modbus RTU 主站（agv_modbus）讲清楚两件事——① 每个函数到底干什么；② 一次读/写从应用一路走到从站、再走回来，整条链路是什么。讲法是「函数表 + 链路方框 + 行号链接」，与工程里《S6A RT 线程》《S7 里程计》《异步日志改造》等分册一致。

学习深度：对齐学习册裁定的 L3「会写主站」（组帧/解帧/CRC/t3.5/异常码/重试/字序/RS485 方向）；不碰 L4（自研协议栈/网关内核）。

无硬件前提：本机无 IMU，对端用纯标准库虚拟从站 tools/sim_imu_modbus.py（pty），与项目里「vcan + sim_motors.py」同思路。

验证状态：单测 46 断言全过；pty 端到端读回 9 个 float32 PASS；故障注入（异常码/坏 CRC/丢帧重试）按预期；make test 与 ctest 全过。

关联：学习册 MODBUS_LEARNING_MAP_print.html（协议原理）、HANDOFF §16.5。成文时间：2026-10-09。

顶层是调用方（未来的 IMU 采集线程或调试程序），往下依次是事务层 → 帧层 → 纯函数层，最底下落到串口驱动。箭头方向就是调用方向；纯函数层不再向下依赖任何东西。

区间/值宏含义是否重试

3.1 一次「读 IMU」的完整链路（mb_read_regs 主线）

场景：应用要读 0x04 输入寄存器的 18 个寄存器（= 9 个 float32）。下面每一格都是一次真实的函数调用，方框下的编号与 §3.3 的步骤表一一对应。

↓ 得到 8 字节请求
④ attempt = 0 .. retries

↓⑦ mb_rx→poll() read()→mb_expected_len 判齐
↓⑧ mb_parse_read_resp→校验 addr/func/字节数→mb_crc16 整帧==0?
↓⑨ 判定→异常? 立即返回/CRC/超时? 重试/成功? 返回 n
↓
⑩ 应用拿到 out[18]→⑪ mb_regs_to_float32 还原 9 个 float

3.3 逐步说明（每步：函数 → 干什么 → 出错会怎样）

步函数 / 行号干什么出错 → 返回
①mb_read_regs事务入口：读 n 个寄存器到 out—
②（函数内校验）检查 func ∈ {0x03,0x04}、1 ≤ n ≤ 125、指针非空MB_E_PARAM（不重试）
③mb_build_read拼出 8 字节请求帧；内部调 mb_append_crc → mb_crc16—
④（for 循环）最多执行 retries+1 次；每次失败重新走 ⑤~⑨循环耗尽 → 最后一次错误码
⑤mb_t35_delay发前静默 ≥ t3.5，让从站把上一帧判完—
⑥mb_tx485 切「发」→ write 全帧 → tcdrain 等末字节移出 → 切「收」写失败 → MB_E_IO（重试）
⑦mb_rxpoll() 等首字节；读满后用 mb_expected_len 判整帧是否齐超时 → MB_E_TIMEOUT（重试）
⑧mb_parse_read_resp校验地址/功能码/字节数；mb_crc16 整帧为 0 才算过；异常响应转 MB_ERR_EXCCRC/帧错 → 负码（重试）；异常 → 立即返回
⑨（分支判定）异常立即返回；CRC/帧/超时计一次失败并重试；成功清零失败计数—
⑩（回到调用方）返回 n，out[] 内为各寄存器—
⑪mb_regs_to_float32可选：每两个寄存器按字序还原一个 float32—

3.4 三条分支（同一段循环，走向不同）

  • 正常路径：⑤→⑥→⑦ 收齐 → ⑧ CRC 通过 → 返回值 n，mb_note_ok 清零连续失败。
  • 传输问题（超时 / CRC 错 / 帧不合法）：⑦ 或 ⑧ 报负码 → mb_note_fail → 回到 ④ 重试；重试耗尽则把最后一次错误码返回。这是「可恢复」错误。
  • 从站异常（如非法地址 0x02）：⑧ 解析出 MB_ERR_EXC(2) → 立即返回、不重试。这是「配置错误」，重试无意义，只会拖慢轮询。

3.5 一次「写（0x06）」的链路（差异点）

mb_write_reg(ctx,reg,val)→mb_write_common→mb_build_write_single→mb_append_crc→mb_crc16
↓mb_t35_delay→mb_tx→mb_rx→mb_parse_write_resp（校验回显+CRC）
↓成功返回 1/异常(5字节)单独分支 → 立即返回

与读的差异只有两处：① 组帧用 mb_build_write_*；② 解帧用 mb_parse_write_resp 校验「回显」——0x06 要求从站把「地址+值」原样回显，0x10 回显「起始地址+数量」，以此确认写入落点。

3.6 谁在保护谁：为什么不用加锁

每个 mb_ctx_t 对应一条串口，一次事务从 mb_t35_delay 到收帧结束是顺序执行、不可重入的。因此约定：一个 ctx 只由一条线程使用（下一阶段的 IMU 采集线程）。这与工程里「RT 线程独占 CAN 收发」是同一约定，避免了在最底层再引入锁。

§5 float32 四种字节序

IMU 的 0x04 区每个量是 float32 = 2 个 16 位寄存器。约定 r0 为低地址（先读到）、r1 为高地址；要把它们还原成内存序 A B C D（大端 IEEE754）：

表 5-1　四种字序（以 1.5f = 0x3FC00000，字节 3F C0 00 00 为例）
字序r0（低地址）r1（高地址）含义
ABCD0x3FC00x0000大端：r0=AB, r1=CD（最常见）
CDAB0x00000x3FC0字交换：r0=CD, r1=AB
BADC0xC03F0x0000字节交换：r0=BA, r1=DC
DCBA0x00000xC03F全小端：r0=DC, r1=BA

踩过的坑（值得记）：第一版把按字序拼出的 4 个字节直接 memcpy 进 float，结果 1.5f 读出 6.9e-41。原因：这 4 个字节是大端数值序，而 ARM/x86 是小端存放，直接搬运等于整体颠倒。正确做法是先拼 32 位整数再解释（agv_modbus.c#L150-179）：

uint32_t v = ((uint32_t)b[0] << 24) | ((uint32_t)b[1] << 16)
           | ((uint32_t)b[2] << 8)  | (uint32_t)b[3];
float f; memcpy(&f, &v, sizeof f); return f;

§6 返回码设计（一个负数里塞三类信息）

本模块不依赖 agv_log（与 agv_queue/agv_pool 同一分层原则），错误全走返回码。难点是既要报「本地错误」又要报「从站异常码」，还不能撞车，于是分区（见 §1.4 表）：

#define MB_ERR_EXC(code)  (-(int)(0x100 | ((code) & 0xFF)))   /* 0x02 → -258 */
#define MB_IS_EXC(r)      ((r) <= -257 && (r) >= -511)
#define MB_EXC_CODE(r)    ((-(r)) & 0xFF)                      /* 取回异常码 */

-1..-5 是本地错误，-257..-511 是从站异常，二者绝不重叠；调用方一句 if (MB_IS_EXC(rc)) 就能区分「传输失败（可重试）」和「从站拒绝（不可重试）」。

§8 几个容易踩的坑

  • 半双工「发完立刻切收」会吞首字节：write() 返回 ≠ 末字节已移出；必须 tcdrain() 后再切收（mb_tx 已封装）。
  • 异常不能当丢包重试：0x02 非法地址 是配置错，重试无意义；只有超时/CRC/帧错才重试。
  • 字序不是「小端」那么简单：四种组合，且还原时要「拼大端整数再解释」，不能直接 memcpy 字节数组。
  • CRC 低字节先发：算出的 0x0BC4 上线是 C4 0B；收帧用「整帧 CRC==0」校验最省事。
  • 一帧的边界靠 t3.5 静默：两次事务之间必须留够静默，否则从站会把两帧粘在一起。
  • 一个 ctx 一条线程：事务不可重入，别在同一串口上并发调用。
