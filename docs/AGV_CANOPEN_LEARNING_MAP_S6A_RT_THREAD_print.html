§0 一页地图：这次改造到底改什么

先说结论：这份工程现在的 Makefile 是「单线程模式」，第 5 站讲的那条 RT 线程根本没被编译进来。所谓「实时性改造」，第一步就是把它打开，第二步给它一个实时优先级。

    │

  ┌──────────────────────────────────────────────┐
  │  单线程：只有主线程，100ms 一圈                │
  │  收 CAN 帧 / 处理 PDO / 跑 SDO / 写日志 ……    │

先明确一个概念：这里的「实时」不是「快」，而是「准」。是「每 1ms 一定跑一次，最坏情况也不超过某个上限」。跑得平均很快但偶尔卡 20ms，这在实时系统里叫失败。

§1 为什么非要把这件事单独拆出来

1.1 本工程有两个节拍

表 6A-1　两条线程的节拍
节拍宏 / 位置干什么
100ms（慢）MAIN_THREAD_INTERVAL_US，CO_main_basic.c:60主线程。跑 SDO 服务/客户端、NMT、心跳、EMCY、TIME、网关命令行。这些都是「用户交互 / 诊断」性质，慢一点无所谓。
1ms（快）TMR_THREAD_INTERVAL_US，CO_main_basic.c:63RT 线程。只管「收 CAN 帧」和「SYNC / RPDO / TPDO」。这是每次运动控制都要走的通道，必须准时。

1.2 为什么不能「一根线 100ms 包打天下」

因为 CAN 帧是「随时到」的，不是「到点来」的。右电机那帧 0x38A（第 4 站讲过：状态字 + 实际位置）可能在你正处理 SDO 请求、正要写日志的任意时刻到达。

单线程下的连锁反应是：

一帧 0x38A 到达
   │
   ▼
socket 收包缓冲区（内核里排队，能存几百帧）
   │
   │  ← 主线程此刻正在干别的：算 SDO、写日志、等网关输入……
   │     这帧只能**在缓冲区里等着**
   ▼
主线程忙完这一圈（最多要等 100ms），才回头把帧取走
   │
   ▼
「收到帧 → 处理完」的延迟 = 不确定（可能几 µs，也可能几十 ms）

这就是问题所在：延迟没有上限。对 AGV 来说，位置反馈晚到 50ms 和晚到 5ms，是两种完全不同的车。

1.3 抖动的直觉：平均对 ≠ 每次都对

目标节拍：|← 1ms →|← 1ms →|← 1ms →|← 1ms →|

情况 A（好）：│**│**│**│**│         每次都很接近 1ms —— 抖动小
情况 B（坏）：│*│******│*│****│     平均下来也是 1ms，但单次忽快忽慢 —— 抖动大

实时性看的是「最坏那一次」，也就是情况 B 里那个最长的一格。所以在下篇里，我们统计抖动时重点看 max（最大值），而不是平均值。

1.4 拆成两条线程之后，谁保护谁

改造完的分工是这样的（主线程管杂事，RT 线程管节拍）：

一条 can0 总线
      │
      ├───────────────────────────────┐
      ▼                               ▼
 RT 线程（epRT，1ms）            主线程（epMain，100ms）
 SCHED_FIFO 高优先级             SCHED_OTHER 普通优先级
      │                               │
 · 收 CAN 帧（0x38A / 0x38B）    · SDO 服务/客户端
 · SYNC / RPDO / TPDO 处理        · NMT / 心跳 / EMCY / TIME
 · app_programRt（应用钩子）       · 网关命令行（-c stdio）
      │                               │
      └──────── 共用一个 OD ──────────┘
              （用锁 CO_LOCK_OD 保护）

关键点：RT 线程优先级高，主线程干活干得再久，也抢不走 RT 线程的时间片。反过来，RT 线程跑完就阻塞在 epoll 上，把 CPU 让回给主线程。这样「杂事」就再也拖不累「节拍」了。

§3 改造第二步：给 RT 线程一个实时优先级（-p）

打开多线程后，RT 线程默认还是「普通线程」（SCHED_OTHER），照样会被别的进程抢。要让它「有事就立刻执行」，得给它 SCHED_FIFO 实时调度策略 + 一个优先级数字。

3.3 if(rtPriority > 0) 为什么这么写

rtPriority 默认 -1（:278），含义是「用户没传 -p」。逻辑链条是：

-p 没传          → rtPriority = -1  → :421 跳过校验，:730 条件为假 → **不设策略**（线程保持 SCHED_OTHER）
-p 0             → :421 校验失败（0 < 1）→ **直接报错退出**（0 在 SCHED_FIFO 里是非法值）
-p 1 .. -p 99    → :421 通过        → :730 条件为真 → **设成 SCHED_FIFO**

所以到 :730 时，rtPriority 只可能是 -1 或 1~99。> 0 就等价于「用户确实想要实时优先级」。

坑：没有权限，-p 会让进程直接退出。给线程设 SCHED_FIFO 需要 root 权限（或 CAP_SYS_NICE 能力）。普通用户执行 pthread_setschedparam 会返回 EPERM，而代码在 :735-739 的处理是「打 CRIT 日志 + 置退出标志」，于是程序立刻结束。

两种解法：① sudo ./canopend ...；② 一次性授权：sudo setcap cap_sys_nice+ep ./canopend，之后普通用户也能跑。

3.4 SCHED_FIFO 到底是什么

Linux 有三种常见调度策略，区别在「谁来抢谁」：

表 6A-5　三种调度策略
策略规则本工程用在哪
SCHED_OTHER默认的「分时」策略。所有普通进程排队轮流用 CPU，公平但延迟不确定。主线程（不设，就是它）
SCHED_FIFO实时策略。只要它有活干，就立刻抢占所有 SCHED_OTHER 线程；同级之间按「先到先跑，跑完/主动让出才轮到下一个」，不会被打断。RT 线程（-p 设的）
SCHED_RR也是实时策略，但同级之间按时间片轮转（round-robin）。本工程没用
 
【SCHED_FIFO:80 的 RT 线程 vs 普通线程】

 就绪队列（数字大 = 优先）
   ┌───────────────────────────────┐
   │ SCHED_FIFO 80  │ RT 线程       │  ← 只要它是「就绪」态
   ├───────────────────────────────┤     立刻上 CPU，别人全让开
   │ SCHED_FIFO 1   │ （无）        │
   ├───────────────────────────────┤
   │ SCHED_OTHER    │ 主线程/别的进程│  ← 只有在没有就绪的实时线程时才能跑
   └───────────────────────────────┘

 时间轴：
   主线程跑 ────────┬───────────────┬────────── 继续跑
                    │ RT 定时到点     │
                    ▼   （内核立刻切过去）
              [RT 线程执行 1ms 的活] ──► 干完阻塞在 epoll_wait
                                          │
                                          ▼  交还 CPU
                                     主线程接着跑

为什么这套是安全的（不会卡死系统）？因为 rt_thread() 里是一个「CO_epoll_wait 阻塞 → 处理 → 再阻塞」的循环（CO_main_basic.c:888-907）。它不忙等：没事件时线程是「睡眠」状态，CPU 完全还给别人。只有当 1ms 定时到点、或 CAN 帧到达、或被唤醒时才短暂占用 CPU。

3.5 优先级数字该给多少

表 6A-6　优先级取值建议
取值说明
为什么不用 9999 是实时最高档，会和内核的一些高优先级线程（如中断迁移、看门狗）同级甚至压过它们，风险大。
为什么常给 80 左右足够高（稳压过所有普通进程），又给内核线程留了空间。够用就好，不必顶格。
为什么主线程不提优先级主线程跑 SDO/日志/网关，允许被抢占。它的活晚一点没关系；只要它别去拖 RT 线程——而提了 RT 优先级之后，它想拖也拖不动了。

4.2 跨线程「敲门」：wakeupCallback + eventfd

两个线程各自阻塞在自己 epoll 上，怎么互相通知？靠 eventfd。开线程后，CO_epoll_interface.c:241-288 会给每个慢速模块（NMT / 心跳 / EMCY / SDO 服务端 / SDO 客户端 / TIME）注册一个回调 wakeupCallback（定义在 CO_epoll_interface.c:226）。

主线程里某个模块状态变了（比如 SDO 服务端收到了请求）
        │
        ▼
   wakeupCallback()  →  往 event_fd 写一个数
        │
        ▼
   RT 线程的 epoll 被唤醒 → CO_epoll_wait 检测到 event_fd 事件
        │
        ▼
   （不是定时事件，所以 timerEvent=false）
   如果是纯唤醒事件，CO_epoll_processRT 不会重复跑 PDO
   （靠 CO_epoll_interface.c:329 的 if (!realtime || ep->timerEvent) 把关，下篇详讲）

单线程模式为什么不需要这套？因为只有一个线程，不存在「叫醒对方」的问题，所以 :241-288 这整段唤醒注册被 #ifndef CO_SINGLE_THREAD 包着，单线程时是空函数。

  1. 现状是单线程：Makefile:54 定义了 -DCO_SINGLE_THREAD=1，第 5 站讲的那条 RT 线程根本没被编译进去，收帧和 PDO 都挤在主线程 100ms 的循环里，延迟无上限。
