§1 RT 线程靠什么被「准时叫醒」

1.1 三件套：epoll + eventfd + timerfd

RT 线程的核心是这一句（CO_main_basic.c:890）：CO_epoll_wait(&epRT)。它内部就是「睡到有事发生」。能让它醒来的有三路事件，全部由一个 epoll 管着，这个 epoll 在 CO_epoll_create（CO_epoll_interface.c:68）里搭好：

CO_epoll_create(&epRT, 1000)                 ← 参数：定时器周期 1000µs（= 1ms）
   │
   ├─ epoll_fd  = epoll_create(1)                    (CO_epoll_interface.c:78)
   │     「事件容器」。下面几个 fd 都注册到它里面，一次 epoll_wait 就能等所有来源。
   │
   ├─ event_fd  = eventfd(0, EFD_NONBLOCK)           (:85)  → epoll_ctl ADD (:92)
   │     「门铃」。别的线程想叫醒本线程，就往它写一个数（见上篇 §4.2 wakeupCallback）。
   │
   ├─ timer_fd  = timerfd_create(CLOCK_MONOTONIC)    (:99)  → epoll_ctl ADD (:115)
   │     「节拍器」。由内核计时，到点自动通知，不需要谁去轮询。
   │        tm.it_interval = 1000µs                  (:104-105)  ← 之后每 1ms 自动重复
   │        tm.it_value    = 1ns                     (:106-107)  ← 首次几乎立刻触发
   │        timerfd_settime(...)                     (:108)
   │
   ├─ ep->timerInterval_us = 1000                    (:120)  记下目标周期
   ├─ ep->previousTime_us  = 当前时间(单调时钟)        (:121)  给下一圈算时差用
   └─ ep->timeDifference_us = 0                      (:122)
            │
            ▼
   CO_epoll_wait(&epRT)  →  epoll_wait(epoll_fd, &ev, 1, -1)   (CO_epoll_interface.c:149)
                             └─ 超时参数 -1 = 一直阻塞，直到有事件
表 6B-1　三个 fd 各是什么
fd是什么 / 谁触发醒来后干什么
timer_fd内核定时器（timerfd）。每 1ms 由内核自动触发一次。来源是「时间」。置 ep->timerEvent = true（:188），表示「这次是到点醒的」→ 允许跑 PDO。
event_fd线程间门铃（eventfd）。别的线程写一个数就响。来源是「软件通知」。只把数据读掉（:173），timerEvent 保持 false → 不会因为被叫醒就多跑一次 PDO。
CAN 收帧 fdCAN 套接字。挂在 RT 的 epoll 上（CO_main_basic.c:561）。来源是「CAN 帧到达」。由 CO_CANrxFromEpoll 把帧读走（见 §2）。

1.2 为什么用 timerfd，不用 sleep / usleep

表 6B-2　定时方式对比
方式问题 / 优势
usleep(1000) 循环① usleep 是「睡这么久」，醒来时刻不保证；② 会累积漂移：每次多睡一点点，误差越滚越大；③ 睡之前你还得先把活干完，没法「到点就跑」。
timerfd + epoll① 内核按 it_interval 的绝对节拍推进，不累积漂移；② epoll_wait 一次就能等三路事件（定时 / 门铃 / CAN 帧），不用写轮询死循环；③ 没事件时线程真在睡眠，不占 CPU。

关键理解：it_interval 是「周期」，it_value 是「下一次触发的延时」。本例 it_value = 1ns（:107），意思是「创建后几乎立刻触发第一次」，之后按 it_interval = 1000µs 自动重复，不需要每圈重新设置。

1.3 应用可以「提前」下一圈：timerNext_us

有些活等不到下一圈定时。比如主线程刚发了 CAN 帧，希望「尽快」再进一次循环去把发送队列冲掉。为此 CO_epoll_processLast（CO_epoll_interface.c:192-219）做了一件事：如果本轮有人把 timerNext_us 改得比 timerInterval_us 小，就用 timerfd_settime 把「下一次触发」提前。

谁改小了 timerNext_us？
  CO_epoll_interface.c:307-308  CO_epoll_processMain 里：
      if (co->CANmodule->CANtxCount > 0 && ep->timerNext_us > CANSEND_DELAY_US)
          ep->timerNext_us = CANSEND_DELAY_US;      ← 100µs（CO_epoll_interface.c:55）

逻辑：还有没发完的 CAN 报文 → 把下一圈的等待压到 100µs → 尽快回来继续发
      │
      ▼
CO_epoll_processLast（:204）if (timerNext_us < timerInterval_us)
      → timerfd_settime 设成一次性、且在 :208-213 转成秒/纳秒
      （注意 :206 有个 +1µs，防止算出 0）

这解释了为什么主线程的节拍虽然是 100ms，但「有报文待发」时实际不会老老实实等 100ms。

§2 现成的测量点：timeDifference_us

抖动统计不用自己造时钟——工程里每圈都已经算好了「上一圈实际花了多久」。就在 CO_epoll_wait（CO_epoll_interface.c:143）里，四行代码：

CO_epoll_wait(CO_epoll_t *ep) {
    ...
    epoll_wait(ep->epoll_fd, &ep->ev, 1, -1);          // :149  一直睡，直到有事
    ep->epoll_new  = true;                             // :150
    ep->timerEvent = false;                            // :151

    uint64_t now = clock_gettime_us();                 // :154  现在（单调时钟，不会被改系统时间影响）
    ep->timeDifference_us = (uint32_t)(now - ep->previousTime_us);  // :155  ★本圈实际耗时
    ep->previousTime_us   = now;                       // :156  记下来，给下一圈算

    ep->timerNext_us = ep->timerInterval_us;           // :158  默认下圈还是 1ms（除非有人改小）
    ... （后面按事件类型分支：event_fd / timer_fd）
}

把这条时间线画出来最直观：

RT 线程时间轴：
  ────────────────────────────────────────────────────────────────────►  时间
        ▲                          ▲                          ▲
   epoll_wait 返回             epoll_wait 返回             epoll_wait 返回
     （上一圈）                    （本圈）                    （下一圈）
        │                          │                          │
        └──── 干活：收帧 ─► SYNC/RPDO/TPDO ─► app_programRt ───┘ 干活 ───┘
               ↑__ 这一段就是「一圈」__↑

  timeDifference_us（本圈）= 本圈返回时刻 − 上圈返回时刻      （:155）
  理想值 = timerInterval_us = 1000 µs
  抖动   = | timeDifference_us − 1000 |
表 6B-3　timeDifference_us 是谁算的、被谁用
环节位置说明
算出来CO_epoll_interface.c:154-155用 clock_gettime_us()（:61，取 CLOCK_MONOTONIC 单调时钟）做差。
被 RT 逻辑用CO_epoll_interface.c:337 / 341 / 345喂给 CO_process_SYNC / RPDO / TPDO，做「距上次过了多久」的时间补偿。
被应用用CO_main_basic.c:904app_programRt(CO, epRT.timeDifference_us) —— 本站的统计就写在这里面。

顺手记一个把关点。CO_epoll_interface.c:329：

if (!realtime || ep->timerEvent) {  ...跑 SYNC / RPDO / TPDO...  }

RT 线程调用时 realtime = true（CO_main_basic.c:891），所以条件变成「只有 timerEvent 为真才跑 PDO」。也就是说：被 eventfd 叫醒那种「非定时」唤醒，不会白跑一趟 PDO——避免同一节拍内重复处理。反之，如果哪次是 CAN 帧唤醒（也不是定时事件），同样不跑 PDO，只把帧收进来，交给本圈或下一圈的定时事件处理。

§3 抖动从哪来

理想情况下 timeDifference_us 永远等于 1000。现实中它会摆动。下面是主要原因（按「自己造的」和「系统给的」分开）：

表 6B-4　抖动来源与对策
来源为什么会抖表现对策
调度延迟更 urgent 的活占着 CPU，你的线程醒来了但上不了 CPU偶发大尖峰上篇的 SCHED_FIFO 提优先级
缺页 / 内存分配运行时才真正分配物理页，触发缺页处理，卡在 syscall 里头几圈特别慢mlockall(MCL_CURRENT|MCL_FUTURE) 提前锁内存；避免在 RT 线程里 malloc
CPU 降频省电调频（governor）让频率忽高忽低整体偏慢、周期性波动调成 performance governor
中断网卡/CAN/定时器中断打断当前执行微秒级散布中断亲和性（irq affinity）绑到别的核
跨核迁移线程被调度器在不同 CPU 核间搬来搬去，缓存全失效随机中等尖峰sched_setaffinity 绑到固定核
日志 / 文件 IOprintf/openlog/写盘会阻塞，且要拿锁大尖峰RT 线程里尽量不写日志；要写就累积到内存、交给主线程

最常见的坑，是自己造的抖动。RT 线程里出现下面任一操作，抖动一定大：printf / log_printf（要拿 stdio 锁、可能写终端）、malloc/free（可能触发缺页）、读写文件、等 mutex。这类操作应全部搬到主线程。

对照一下本工程：rt_thread()（CO_main_basic.c:885-910）里除了收帧和 app_programRt，没有任何日志输出——这正是它抖动小的原因之一。所以你往里加统计时，别在每圈都打印。

4.2 统计什么

按「1 秒一个窗口」统计，四个数就够看清问题：

表 6B-5　四个统计量
量含义怎么看
avg本窗口平均周期接近 1000 说明「平均节拍对了」，但这不代表实时性好。
min本窗口最快一圈太小说明有「提前醒」的情况（如被 eventfd 唤醒）。
max本窗口最慢一圈最重要。实时性看的就是这个「最坏情况」。
over超过「目标 + 阈值」的圈数直接告诉你：有几次没达标、有多频繁。

4.3 代码骨架（可直接抄，再接自己的日志）

/* CO_application.c 里 app_programRt 的改造版（示意，注释为中文） */
#include <stdio.h>

void app_programRt(CO_t *co, uint32_t timer1usDiff) {
    (void) co;

    static uint32_t n;                  /* 本窗口内已经过了多少圈 */
    static uint32_t sum;                /* 本窗口耗时累加 */
    static uint32_t mn = 0xFFFFFFFFu;   /* 本窗口最小周期（初值给个很大的数） */
    static uint32_t mx;                 /* 本窗口最大周期（重点看它） */
    static uint32_t over;               /* 超过阈值的圈数 */
    static uint32_t acc;                /* 累计耗时，用来判断是否满 1 秒 */

    n++;  sum += timer1usDiff;  acc += timer1usDiff;
    if (timer1usDiff < mn) mn = timer1usDiff;
    if (timer1usDiff > mx) mx = timer1usDiff;
    if (timer1usDiff > 1000 + 200) over++;   /* 目标 1000µs；超过 200µs 记一次 */

    if (acc >= 1000000) {                     /* 累计满 1 秒，输出一行并清零 */
        printf("RT: n=%u avg=%u min=%u max=%u over200=%u us\n",
               n, sum / n, mn, mx, over);
        n = 0; sum = 0; mn = 0xFFFFFFFFu; mx = 0; over = 0; acc = 0;
    }
}

跑起来会看到类似这样的输出：

RT: n=1000 avg=1000 min=993 max=1011 over200=0 us     ← 很稳
RT: n=1000 avg=1001 min=988 max=1320 over200=2 us     ← 有 2 次被拖到 1.3ms，要查
                ▲         ▲        ▲         ▲
             平均对     最快      最慢      超限次数（真正要盯的）

关于 printf：它在 RT 线程里不是零风险（要拿 stdio 锁）。但本骨架一秒才打一行，影响可以忽略。若要更严谨：把每圈数值存进一个环形数组，只在主线程的 app_programAsync（CO_main_basic.c:811）里统一打印。

§5 另一把尺子：单帧接收延迟（SO_TIMESTAMPING）

上面量的是「线程节拍准不准」。还有一种抖动是「帧本身晚到了」，要用另一把尺子量：内核收到帧的时刻 vs. 应用取到帧的时刻。

表 6B-6　时间戳链路
环节位置做什么
打开时间戳CO_driver.c:322-330对 CAN 套接字 setsockopt(SO_TIMESTAMPING)，模式是「软件时间戳」（SOF_TIMESTAMPING_SOFTWARE | SOF_TIMESTAMPING_RX_SOFTWARE）。注释里写明：硬件时间戳在很多设备上不靠谱，所以用软件。
内核打戳（内核）内核在收到帧的瞬间记下时间，收在控制消息（cmsg）里。
应用取戳CO_driver.c:822（CO_CANread）用 recvmsg 读，从 cmsg 里解析出：SO_TIMESTAMPING → 时间戳（:855-860）；SO_RXQ_OVFL → 收包队列溢出丢帧计数（:863）。
存起来CO_driver.c:927（CO_CANrxFromEpoll）→ :974把时间戳存进 rxArray[idx].timestamp，供后续（如 trace）使用。

怎么用来量抖动：在收到帧时，用「当前时间 − 帧时间戳」近似「帧从内核到应用」的延迟。配合 §4 的节拍统计，就能区分两类问题：

若节拍统计 max 很大、而单帧延迟正常  → 是「线程被占了 / 调度问题」
若节拍统计正常、而单帧延迟很大      → 是「总线拥堵 / 驱动路径慢 / 收包队列撑了」

两者一起看，才能定位抖动出在哪一段。

注意现状：时间戳在 CO_CANread → CO_CANrxFromEpoll 里已经取出来并存下了，但代码目前没有拿它做任何统计（只是存着）。也就是说，这个开关是「现成可用的测量入口」——正好是本站可以接上的活。

§6 小结 · 自测 · 衔接第 7 站

6.1 本站（下篇）三句话

  1. 定时靠 timerfd + epoll：内核按 it_interval = 1ms 自动推进（不累积漂移），epoll_wait 一次等三路事件（定时 / 门铃 / CAN 帧），没事件时线程真睡眠。
  2. 测量点是现成的：ep->timeDifference_us（CO_epoll_interface.c:155）就是「本圈实际耗时」，理想 1000µs，抖动 = 实际 − 1000。app_programRt 每圈都能拿到它。
  3. 统计写在 app_programRt：按 1 秒窗口记 min/avg/max/超限次数，重点盯 max。改造效果靠「单线程 / 多线程不加 -p / 多线程加 -p」三次对比来证明。

6.2 自测（能答上来就算过）

  1. timerfd 比 usleep 好在哪两点？（提示：漂移、与 epoll 的配合）
  2. it_value = 1ns 和 it_interval = 1000µs 分别管什么？
  3. timeDifference_us 是在哪两个时刻之间做差？为什么它天然就是「本圈耗时」？
  4. 为什么 RT 线程被 eventfd 叫醒时，不会白跑一次 PDO？（提示：CO_epoll_interface.c:329）
  5. 如果统计显示 avg 正常但 max 偶发很大，你应该先怀疑哪些原因？
  6. 为什么在 RT 线程里 printf 会加大抖动？本骨架是怎么规避影响的？

6.3 衔接第 7 站

到这里，第 6 站的两件事都完成了：RT 线程能准时跑（上篇），并且我们能量出它有多准时（下篇）。这条「1ms 准时 → 收两帧 RPDO → 拿到左右轮实际位置」的路已经通了。

但它现在还只是「打印 posR/posL」。第 7 站要做的，是把这两个位置变成有意义的「车在哪」——差速运动学：左右轮位置 → 车体的位移与转角（位姿 x, y, θ）。落点正是同两个钩子：RT 侧的 app_programRt（CO_main_basic.c:904）与收帧钩子 H6064_write（CO_application.c:31）。
