CAN 是广播总线，所有节点挂同一对差分线（CAN_H / CAN_L），谁都能看见所有帧。所以"只收我关心的帧"必须靠过滤器做——这正是链 A 最后要闭麦、链 B 第一跳是过滤器的原因。

3.1 内核里到底存了什么：为什么 optlen=0 就是"闭麦"

只看上面这段用户态代码，很容易怀疑："没给过滤器" 不就是 "不过滤" 吗？ 答案藏在内核 socket 的默认状态里（Linux v5.15 net/can/raw.c）：

raw_init()                        /* socket(PF_CAN, SOCK_RAW, CAN_RAW) 建好那一刻 */
    ro->dfilter.can_id   = 0;
    ro->dfilter.can_mask = 0;     /* MASK_ALL：不分 ID 一律匹配 */
    ro->filter = &ro->dfilter;
    ro->count  = 1;               /* 默认就有 1 条全放行过滤器 */

raw_setsockopt(CAN_RAW_FILTER)    /* 我们调 setsockopt 时进的分支 */
    count = optlen / sizeof(struct can_filter);
    ...
    ro->count = count;            /* optlen=0 → count=0 */

raw_bind() → raw_enable_allfilters()
    for (i = 0; i < ro->count; i ++)
        can_rx_register(..., filter[i].can_id, filter[i].can_mask, ...);  /* 一条条向内核登记 */

把这三段连起来，三件事就通了：

① 默认不是"没有过滤器"，而是"有 1 条全 0 过滤器"。 内核的匹配写法是 (can_id ^ filt.id) & filt.mask；mask=0 时这个与运算恒为 0，永远算"匹配"。所以刚 socket() 完什么都不设，本来就能收到所有帧——靠的就是那条第 {id:0, mask:0} 的默认项。

② optlen=0 是把这张表换成空表，不是"不改动"。 内核按 count = optlen / sizeof(can_filter) 数条数，长度 0 → count=0，登记循环一次都不进 → 内核里一条过滤器都没有 → 任何帧都不匹配 → 全部丢弃。disableRx() 要的正是这个效果。

③ 所以 mask=0 的项必须剔除。 rxFilter[] 是 calloc 出来的（CO_driver.c:237），没被登记过的槽位就是 {0,0}；若整张表原样下发，这些 {0,0} 项个个"放行一切"，等于白闭麦。setRxFilters() 里那句 can_id!=0 || can_mask!=0（:139）就是专门把它们丢掉。

一个流传很广的说法要纠正：网上（乃至一些 AI 回答）说 setsockopt(..., CAN_RAW_FILTER, NULL, 0) 是"清空过滤器 = 接收所有帧"。这与内核源码和实测都不符：空列表 = 一条都不收。之所以容易记反，是把"默认收全部"和"显式设空"混为一谈——默认收全部，是因为默认有一条 {0,0} 项，而不是因为"列表为空"。真要"什么都要"，是传一条 {can_id:0, can_mask:0}，而不是传长度 0。

新手最常踩的坑：CO_CANsetConfigurationMode()（CO_driver.c:171）是空函数，什么都不做；唯一开闸入口是 CO_CANsetNormalMode()。若日志有 running ... 却一帧都收不到，先查它有没有被调到、rxFilter[] 是不是空。

第 1 跳（内核按 CAN_RAW_FILTER 筛）不匹配的帧直接被丢，压根不通知程序；这层软件匹配是"万一漏进来再兜一次"，思路和内核过滤器完全一样。

补一句：CO_epoll_wait()（CO_epoll_interface.c:149）写的是 epoll_wait(fd, &ev, 1, -1)——一次只取 1 个事件，所以每轮最多处理一帧，剩下的留给下一轮。这也解释了为什么第 5 站关心"一轮多久"。
