第 8 站 · Qt 上位机：位姿显示与指令下发

本站定位：阶段 C「上位机 & 上板」的第一站。前七站全在从站（板子）一侧：收帧、协议、实时、里程计。算出来的位姿 x,y,θ 目前只活在本进程的静态变量里，外网看不到。本站搭一个 Qt 上位机，把它显出来，并能对节点下几条命令。

一句话概括：不去重写一套网络协议，而是直接复用 canopend 自带的 CiA 309-3 ASCII 网关——它把「对象字典读写」变成「一行文本」，Qt 只要连上它的 socket、发一行、读一行。

为什么值得单独一站：① 这是工程里第一次出现「人机界面」，是简历上最好讲的一环；② 它牵出两个真实工程问题——协议怎么复用（别自己造轮子）和跨线程怎么取数（RT 线程写、界面线程读，必须加锁）；③ 它是第 9 站「交叉编译上板」的直接前置（界面跑在 PC，节点跑在板子）。

阅读顺序：§1 讲界面要什么、数据从哪来（不看代码）→ §2 讲板端那一半（网关服务端）→ §3 讲客户端原型 cocomm → §4 才是 Qt 侧架构 → §5/§6 诚实交代缺口与联调。

3.2 收发：一个「发一行、读一行」的循环

write(fd_gtw, commBuf, len);   // 发一行命令
printReply(fd_gtw);            // 阻塞读一行回复，解析
表 8-11 printReply() 的解析规则（出处 cocomm.c:92-198）
判断含义
含 "] ERROR:"出错，打到 stderr。
含 "] OK\r\n"成功（写类/动作类）。
否则取 "] " 之后到 "\r\n" 之间那就是读到的数值，打到 stdout。
它把「状态」和「数据」分开：错误走 stderr、数值走 stdout。所以终端里能 cocomm "1 r 0x6064 0 i32" > pos.txt 只拿数。Qt 侧也应照这个思路——一次交互拆成「成功/失败」+「负载值」两件事处理。
两个必须抄走的坑：① signal(SIGPIPE, SIG_IGN)（[:319-322](file:///home/zcy/Project/panasonic_canopen_agv/cocomm/cocomm.c#L319-L322)）——客户端也会在对方断开时被 SIGPIPE 杀掉，必须忽略；② 命令没写序号 [n] 时要自动补 [<i>] （[:456-459](file:///home/zcy/Project/panasonic_canopen_agv/cocomm/cocomm.c#L456-L459)），否则网关认不出这是新命令。

§4 Qt 侧架构：UI 线程 与 通信线程 分离

4.1 为什么必须分线程

socket 的 read() 是阻塞的（cocomm 里就是裸阻塞读）。如果直接在 Qt 的 UI 线程里循环读，窗口会卡死、按钮不响应。所以标准做法是：

┌────────────── Qt 主线程（UI） ──────────────┐
│  MainWindow                                   │
│   ├ 控件：位姿数值、轨迹画布(QPainter)          │
│   └ 槽：onPoseUpdated(x,y,th)  ← 只负责"画"    │
└───────────────▲──────────────────────────────┘
                │ 跨线程信号槽（Qt 自动排队投递）
                │ signal poseUpdated(double,double,double)
┌───────────────┴──────────────────────────────┐
│  工作线程：CommWorker                          │
│   ├ QTcpSocket（或 QLocalSocket）              │
│   ├ 定时器 QTimer：每 N ms 发一条 "1 r ..."     │
│   ├ 收：readyRead() → 解析 → 拼出一帧位姿       │
│   └ 发：按钮触发 → 组命令字符串 → write()       │
└───────────────────────────────────────────────┘
关键点：Qt 的「信号槽 + QueuedConnection」天生解决跨线程，不需要自己加锁（别把 socket 和界面控件塞进同一个线程再手动锁，那是最常见的新手错）。工作线程只管「收发+解析」，主线程只管「显示」。

§5 位姿怎么从板子出去：本站唯一的板端增量

5.1 诚实交代现状

现状：第 7 站算出的 odom_x/odom_y/odom_th 是 CO_application.c 里的 static 变量（[:52-59](file:///home/zcy/Project/panasonic_canopen_agv/CO_application.c#L52-L59)），它们不在对象字典里。而网关只能读「对象字典里的东西」。查 [OD.h:54-64](file:///home/zcy/Project/panasonic_canopen_agv/application/OD.h#L54-L64) 的 OD_CNT_ARR_* 列表：只有 1003/1010/1011/1016/607B/607D/.../60FE，没有任何 0x2xxx 厂商数组。所以「Qt 一上来就读到位姿」这件事，现在还差一步。

5.2 三条补法（按工作量排序）

表 8-13 把位姿暴露出去的三种做法
做法怎么做代价 / 适用
① 新增 OD 数组条目（★推荐起步）在 OD.c/OD.h 加一个厂商段数组（如 0x2100 存 x/y/th），在 app_programRt 里写它。Qt 用 1 r 0x2100 1 r32 轮询读。改动小、复用现成网关；SDO 是偶发请求，实时性一般。适合「看一眼 / 画轨迹」。
② 用 TPDO 主动上报映射一个 TPDO 带位姿三项，靠 100ms 的 SYNC（第 5 站：0x1006=100000µs 已在发 0x080）周期广播。延迟低、周期准；要改 OD + TPDO 映射，Qt 侧还得会收 CAN——复杂，暂不必。
③ 板端自写 TCP 直推不用网关，另开线程把位姿按自定义格式推给 PC。最灵活但要自维护协议，等于放弃 §2 的白捡便宜。不推荐。

5.3 加进 OD 时绕不开的两件事

  1. 跨线程加锁：位姿由 RT 线程写（app_programRt，[:209](file:///home/zcy/Project/panasonic_canopen_agv/CO_application.c#L209)）、由 主线程读（网关处理 SDO 时）。这正是第 7 站 §5 埋的伏笔——写侧/读侧都必须用 CO_LOCK_OD() / CO_UNLOCK_OD() 包住。第 7 站内部闭环不跨线程，所以那时不加锁是对的；本站是真正引入锁的地方。
  2. 别在 RT 拍里做重活：只做「把三个 double 写进 OD 条目」这一下即可，不要在里面格式化字符串、不要打印（第 7 站 §4.6 的 warn：每拍 printf 会毁掉第 6 站的实时性）。
为什么不用现成的 0x6064（实际位置）？ 因为那是单个电机的原始计数，不是「车在世界里的 x,y,θ」。要知道车在哪，必须走第 7 站的差速运动学。0x6064 只能当「轮子转了多少」用。

5.4 「发指令」这条功能，边界在哪（必须说清）

能做：通过网关下发协议层命令——1 start / 1 stop / 1 preop / 1 reset node（NMT），以及 SDO 写任何 OD 条目。
不能做：让 AGV「按速度/按目标点跑起来」。原因见第 7 站后的结论——本工程全链路「只收不发」，没有任何下发速度指令的代码（CO_application.c 里配的 RPDO 都是「收」，OD 里 TPDO 0x1A00 虽预留了 0x6040+0x60FF，但无人触发）。真正的运动指令需要一个控制器站，那是你之前明确选择「先不做」的部分。

所以第 8 站的「发指令」应如实定位为：下协议层命令（启停/复位）+ 用 SDO 做参数读写，而不是「遥控开车」。

6.2 应能回答的问题

  1. 为什么不自己写 CAN 主站，而是用 canopend -c？—— 网关已内置、零新增协议代码，见 §1.2 三条路对比。
  2. -c stdio / local-<path> / tcp-<port> 三种形态分别何时用？—— 终端手敲调试 / 同机客户端 / 跨机 PC。见 §2.1。
  3. 网关收到文本后，具体由谁去访问 CAN？—— CO_epoll_processGtw → CO_GTWA_write → 内部驱动 CO_SDOclient（本机 OD 走 SDO_CLI_LOCAL）。见 §2.4。
  4. 响应怎么区分「成功、值、失败」？—— "] OK" / "] <value>" / "] ERROR:<code>"。见 §2.5 表 8-9、§3.2 表 8-11。
  5. 为什么 Qt 一定要分线程？—— socket read() 阻塞会卡死 UI；用「工作线程收发 + 信号槽投递」即可，无需手写锁。见 §4.1。
  6. 位姿为什么现在读不到、要怎么补？—— 它不在 OD 里（OD.h:54-64 无 0x2xxx 数组）；需新增数组条目并跨线程加锁。见 §5.1/§5.3。
  7. 上位机能「遥控开车」吗？—— 不能，只能下协议层命令。见 §5.4。
