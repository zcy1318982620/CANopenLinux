§1 步骤② · 单元测试（Unit Test）

1.1 它是什么

单元测试 = 把程序拆成最小的可独立验证单元（通常是一个函数），用可控的输入喂进去，再断言输出符合预期。它的价值不在"证明程序对"，而在"改动后能立刻发现哪里坏了"——是后续所有重构的安全网。

  • 可重复：不依赖人工、不依赖硬件，一条命令跑全部；
  • 快：毫秒级，能每次提交都跑；
  • 定位准：失败直接指到函数，不用猜。

1.2 测试金字塔

数量从多到少、粒度从细到粗：单元测试（多、快、便宜）→ 集成测试（中等，测模块间协作）→ 端到端（少、慢、贵，如 vcan 上跑整条 RPDO→OD→里程计）。本工程的 P2 ② 只做最底层的单元测试；整链验证交给 ③（vcan 故障注入）。

1.3 关键前提：可测性设计（纯函数 vs 副作用）

能轻松单测的函数，都是纯函数：相同输入必得相同输出，不读写外部状态。反之，直接依赖全局静态变量、文件、总线的函数很难单测。

本工程的里程计换算就是天然的纯函数：CO_application.c:58 的 ODOM_K_PER_COUNT = 2πr / N，给定"计数差"就能算"轮面位移"。而 H6064_write 有副作用（写 odom_posR_raw 等静态变量），不适合直接测。

可测性重构的常见手法：把"算"从"存"里抽出来。例如把 L584-L596 的积分公式 抽成纯函数 odom_step(prevR, prevL, curR, curL, *x, *y, *th)，即可脱离 RT 线程、脱离 CAN，直接单测中间点法与 32 位回绕。这是本步唯一可能碰到的代码改动，需先和你确认。

1.4 测试替身（Test Double）

当被测代码依赖外部（CAN 对象、CO->、时间、日志），用一个"假货"顶替它，让测试可控。常见五种：

类型作用 / C 语言做法
Dummy 占位只为凑参数，不被真正使用。
Stub 打桩返回固定值。C 里可用函数指针、#ifdef TEST 里的弱符号（__attribute__((weak))）替换掉真实实现。
Spy 间谍记录"被调用了几次、传了什么"，事后断言。
Mock 模拟预设调用期望，不符合就失败（CMocka 支持）。
Fake 假实现功能简化但能跑，如"内存版队列"替代真实队列。

本工程 ② 阶段大多数是纯函数测试，几乎不需要替身——这正是先做单元测试的成本优势。

1.5 C 语言测试框架选型

框架特点适用
零框架 assert + main不引第三方，几十行自造断言宏本工程首选：符合"不引第三方依赖"的既有约束，agv_queue 用例足够简单
Unity单文件、超轻，嵌入式圈最常用想在裸机/交叉环境跑
CMocka支持 mock、多线程断言、异常捕获需要替身和并发场景
Check / Criterion功能全，fork 隔离用例桌面侧较重的测试套件
本工程建议：先用"零框架"（assert + 计数）搭 tests/ 目录，一个 .c 一个可执行，随主构建一起编。等并发用例复杂了再考虑 CMocka，避免过早引依赖。

1.6 环形队列的测试要点（本步核心）

agv_queue.h 定义了 5 个接口：init / destroy / try_push / pop / close。要覆盖的正是它"设计上最容易错"的地方：

用例构造断言（对应源码）
容量取幂init(&q, 3)q.cap == 4（c:16-20 向上取整到 2 的幂）
回绕（wrap）cap=4，push 5 条再逐条 pop5 条按 FIFO 顺序取回，tail 绕回 0（c:77 / c:115 的 &(cap-1)）
满队丢帧push 满 cap 条后再 push 1 条try_push 返回 -1 且 pushed 不变、dropped+1（c:75-85）
关闭后行为close() 后 push / poppush 返回 -1；pop 取空后返回 -1（消费者退出，c:109-112）
非法参数init(NULL,0) / try_push(NULL,...)统一返回 -1，不崩溃（c:12-14 / c:64-66）
数据完整性写入带特征的 agv_logrec_tpop 出的记录与写入的 memcmp 完全一致（c:76 / c:114 是整结构体拷贝）
并发不丢不重1 生产者 try_push + N 消费者 pop，跑若干万轮成功 pop 数 == pushed；pushed + dropped == 生产总次数（c:79 / c:83 的原子计数守恒）
并发用例为什么难写：它本质是概率性的——单次跑通不代表没竞争。要"跑够久 + 跑够多轮"（循环 for 到百万次）才有一点统计意义；真正抓竞争还得靠 §3 的 TSan。单元测试在这里的作用是锁住接口语义（定死"满就丢、关就退"），而不是"证明并发无 bug"。

1.7 里程计的测试要点

把 L578-L596 的积分逻辑 抽成纯函数后，用例设计如下：

用例输入（计数差 dCntR, dCntL）断言
首拍第一帧只记起点，位姿保持 0（c:570-576）
直行dR == dL > 0θ 不变，x 增加 d、y 不变（c:589-590）
原地转dR == -dL位移 d≈0，θ 按 (dR-dL)/b 变化（c:590）
换算标定dCnt = N（一整圈）轮面位移 == 2πr，误差 < 1e-9（用浮点容差，忌 ==）
32 位回绕从 0x7FFFFFFF 跳到 -0x80000000dCnt 或正或负但绝对值小（c:579-580 用 uint32 相减处理回绕）

§2 步骤③ · 故障注入（Fault Injection）

2.1 它是什么

故障注入 = 故意在系统里引入错误，观察它是否按预期"优雅降级"，而不是崩溃或乱动作。它验证的不是"正常路径"，而是容错路径——那些平时永远不会被执行、却决定了安全性的分支。

为什么 AGV 必须做：电机驱动器会掉线、报文会损坏、编码器会回绕。本工程已经写了心跳容错（CO_application.c#L529-L544：任一从站心跳超时 → 强制零速），但"写了"不等于"生效"。故障注入就是去证明它真的生效。

2.2 注入点的分层

错误可以注入在链路的任何一层，层次越低越真实、成本越高：

层例子手段本工程可行性
硬件断线、电压跌落、CAN 终端电阻缺失拔线、可变电源、故障注入夹具需真机，留到联调
驱动/内核收包丢失、错误帧netem、SocketCAN 统计、ip link set ... down部分可用（vcan 可 down）
协议坏 COB-ID、错 DLC、越界值、丢心跳cansend/cangen 造帧；改 sim_motors.py成本最低，本步主战场
应用mock 掉 CO_ 接口返回错误测试替身与单元测试重叠

2.3 CANopen 协议层：具体注什么

注入类型怎么造预期系统行为
丢心跳停发 0x70A(node10) / 0x70B(node11)HBconsumer 超时 → hb_lost → 强制零速 + 日志 [HB] heartbeat LOST（c:531-538）+ 库内自动发 EMCY
DLC 错误发 0x38A 但只带 3 字节映射/解析拒绝或按规范处理，不得越界读；位姿不更新
越界值位置域塞 INT32_MAX / INT32_MIN换算后仍在 double 范围内，位姿跳变可观测但不崩；回绕处理正确（c:579-580）
停发 RPDO停发 0x38A/0x38Bodom_new 不置位 → 不积分（c:567-568），位姿"冻结"而非乱跳
灌帧压测cangen 高频广播RT 线程 try_push 只丢不阻塞，dropped 上升、1ms 节拍不崩（c:68-72）

2.4 造帧工具：can-utils

# 观察总线上正在发生什么（先确认链路基线）
candump vcan0

# 手工发一帧 0x38A：DLC 由 # 后的字节数决定（这里 3 字节 → DLC=3）
cansend vcan0 38A#370200

# 越界值：DLC=6，状态字 0x0237 + 位置 0x7FFFFFFF（小端）
cansend vcan0 38A#3702FFFFFF7F

# 压力灌帧：1ms 一帧持续造 0x38A
cangen vcan0 -g 1 -I 38A -L 6

本工程已有的 sim_motors.py 已带两个"丢心跳"开关（L35-36 的 --drop-hb-r/_l，在 L97-100 生效）。③ 阶段建议在其基础上再加 --bad-dlc / --out-of-range / --flood 等开关，把上面几种注入做成可复现命令。

2.5 可观测性：怎么知道"降级生效了"

  • 日志：心跳状态跃迁只打一次行（c:533-538），既不刷屏又能看见 LOST/OK；
  • EMCY：心跳错误码 0x8130（errorBit 0x1B）由 HBconsumer 库内自动上报，用 candump 能看到；
  • 计数器：agv_queue_dropped()（c:136-142）在 RT 抖动窗口打印，灌帧时它应上升；
  • 位姿：[ODOM] 每秒打印（c:607-613），冻结/跳变一目了然；
  • RT 抖动：灌帧时若节拍仍稳定，说明 try_push 的非阻塞设计成立。
反向用例同样重要：注入后要能恢复——重新发心跳，[HB] heartbeat OK 应出现、运动恢复。只测"掉线"不测"恢复"，会漏掉状态机卡死的 bug。

§3 步骤④ · 内存与线程体检

3.1 要抓的三类病

类别典型症状后果
内存错误缓冲越界读写、use-after-free、double-free、用未初始化内存偶发崩溃、数据被静默改写（最难查）
内存泄漏malloc/calloc 无对应 free，fd/线程未回收长跑内存只涨不降，最终 OOM
并发错误数据竞争、死锁、锁序不一致随机崩溃/卡死，复现率极低

3.2 工具全景与对比

工具类型能检测需重编译 / 代价
ASan
AddressSanitizer		编译期插桩堆/栈/全局越界、UAF、double-free、泄漏（LSan）是（-fsanitize=address）／约 2× 慢，首选
UBSan编译期插桩未定义行为：整数溢出、非法移位、除零、错位对齐是（-fsanitize=undefined）／开销小，可与 ASan 同开
TSan
ThreadSanitizer		编译期插桩数据竞争、锁序问题是（-fsanitize=thread）／慢 5–15×，与 ASan 互斥
Valgrind
memcheck / helgrind		动态二进制翻译越界、未初始化读、泄漏（memcheck）；竞争/锁序（helgrind/drd）否，直接跑现成二进制／慢 10–30×
怎么选：想快速查内存正确性 → ASan+UBSan（快、信息全）；想抓数据竞争 → -fsanitize=thread 重编一版，或 Valgrind --tool=helgrind；不想改构建、只想拿现成二进制体检 → Valgrind memcheck。

3.3 编译开关与运行选项

# —— ASan + UBSan（开发构建，最常用）——
CFLAGS  += -fsanitize=address,undefined -fno-omit-frame-pointer -g -O1
LDFLAGS += -fsanitize=address,undefined
ASAN_OPTIONS=abort_on_error=1:detect_leaks=1:log_path=/tmp/asan \
  ./canopend can0 -i 1

# —— TSan（单独一版，抓数据竞争，不可与 ASan 同开）——
CFLAGS  += -fsanitize=thread -fno-omit-frame-pointer -g -O1
LDFLAGS += -fsanitize=thread

# —— Valgrind（不改构建，直接跑）——
valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes \
  ./canopend can0 -i 1
valgrind --tool=helgrind ./canopend can0 -i 1      # 竞争/锁序

本工程的编译信息由 Makefile 提供（-g -ggdb），加 sanitizer 时不要动业务代码，只加编译/链接开关即可。

3.4 本工程注意点（很重要）

Sanitizer / Valgrind 会严重改变时序，不能拿它判实时性。本工程 rt_thread 是 SCHED_FIFO 的 1ms 节拍线程：
  • ASan 约 2× 慢，通常还能跑，但会放大抖动——只用它查内存正确性，别用它的抖动数字下结论；
  • Valgrind 慢 10–30× 且串行化，1ms 节拍必然崩 → 只能在非实时场景跑（例如临时降低 RT 优先级，或只体检协议栈/日志路径，不苛求节拍）；
  • TSan 也影响时序，但它能抓 agv_queue 与 CO_LOCK_OD 的竞争，价值最高，值得专门跑一版。

本工程要重点看的对象：3 类线程（main / rt_thread / 2 个日志 worker，由 agv_log_init(256,2) 创建）：

  • 线程回收：退出时是否 agv_queue_close → broadcast → worker 的 pop 收到 -1 退出 → join；少一步就是线程/内存泄漏；
  • 配对释放：agv_queue_init 里 calloc 的 buf 必须由 destroy 的 free 配对（c:23 / c:58），互斥量/条件变量也要 destroy（c:56-57）；
  • 退出路径：正常退出与 Ctrl+C 退出两条路径都要测，看是否都干净收尾；
  • 跨线程共享：位姿写侧在 RT、读侧在 main，靠 CO_LOCK_OD（c:601-605）——TSan/helgrind 若有报，先查这里。

§4 三步怎么配合（执行顺序）

  1. 先 ② 单元测试：零依赖、本地可跑、最快见效。先把 agv_queue 的接口语义"锁死"，为后面改动建立安全网。
  2. 再 ③ 故障注入：扩 sim_motors.py + vcan，验证容错分支真的生效、且能恢复。这步最贴近真机风险。
  3. 最后 ④ 内存与线程体检：跑 ASan+UBSan，再单独跑一版 TSan/Valgrind，把前两步暴露的路径在真实运行中复核一遍。
共同目标：每一步都要可自动化、可回归——能一条命令重跑，出问题时能二分定位。做完这三步，本工程就从"能跑通"升级到"经得起折腾"，为真机联调打好底。
