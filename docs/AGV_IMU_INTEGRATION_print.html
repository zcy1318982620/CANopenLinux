§1 链路总览

整条链路解决一件事：把 RS485 上的一帧 Modbus 应答，变成上位机能读到的车体位姿与 IMU 量。链路被切成三段、跨三个线程，每段只管自己的事：

层文件职责运行线程
① 协议层 agv_modbus.h / agv_modbus.c 组帧 / CRC16 / 收发 / 超时重试 / 解帧 / float32 字序还原 / RS485 方向控制 由调用者决定（此处是采集线程）
② 采集层 agv_imu.h / agv_imu.c 20Hz 轮询 IMU、decode 成采样、seqlock 无锁发布快照；不依赖 log/OD 采集线程（pthread，普通优先级）
③ 应用层 CO_application.c / OD.h / OD.c RT 拍无锁取快照 → 互补滤波 → CO_LOCK_OD 内写 0x6FFF + 0x7010 RT 线程（1ms 节拍）

读侧则是 main 线程的 CiA-309 网关：上位机发 SDO upload，网关直接从 OD_RAM 取值回包。

§5 帧格式速查

读请求 (0x04, 起始 0x0000, 18 个)：
  01 04 00 00 00 12 C6 3F                 ← 8 字节，末 2 字节 CRC(低字节先)

正常响应：
  01 04 24 <36 字节数据> <CRC_lo> <CRC_hi>   ← 5 + 2*18 = 41 字节

异常响应（功能码 | 0x80 + 异常码）：
  01 84 02 <CRC_lo> <CRC_hi>               ← 非法数据地址

寄存器→物理量：输入寄存器 0x0000~0x0011 = 9 个 float32，每 2 个 16 位寄存器一个 float，字序由 mb_cfg_t.word_order 决定（默认 ABCD）。

§7 线程边界与无锁

边界机制为什么
采集线程 → RT 线程seqlock（_Atomic uint32_t seq 奇偶 + release/acquire 屏障）写者（20Hz）永不阻塞读者（1ms 节拍）；RT 侧不上互斥量，避免优先级反转与抖动
RT 线程 → main 线程CO_LOCK_OD 保护 OD_RAMOD 是跨线程共享内存，且可能被 PDO 映射；网关/PDO 都在 OD 上读写
同线程内无锁RPDO 写钩子与 app_programRt 同处 rt_thread、同圈先后执行，无并发
seqlock 读循环的写法坑：不能用 do…while + continue。写者更新时 seq 为奇数要走重试，而 continue 会跳过 s2 赋值、随后在循环条件里使用未初始化的 s2（UB，GCC -Wmaybe-uninitialized 会报）。这里改用 for(;;) + s1==s2 才 break（agv_imu.c:71-91）。

§8 互补滤波

odom_th += (1.0 - AGV_IMU_FUSE_ALPHA) * wrap_pi((double)imu.yaw - odom_th);
odom_th  = wrap_pi(odom_th);
  • α=0.98：短时信里程计（高频、平滑），长时被 IMU 的绝对航向慢慢拉正，消掉里程计累积漂移。
  • wrap_pi 必不可少：yaw 与 θ 在 ±π 附近跳变，差值必须先折到 (-π,π]，否则会整圈拉错。
  • 降级：agv_imu_get()==0 或 agv_imu_offline() 时整段跳过，行为与接入前一致。

§10 踩坑清单

  • float32 还原必须 memcpy：先拼 uint32_t 再 memcpy 进 float，不能把 uint16_t* 强转成 float* 解引用（对齐/别名 UB）。
  • CRC 低字节先发：mb_append_crc 的顺序与从站不一致会导致每帧 MB_E_CRC。
  • 异常响应不重试：MB_ERR_EXC 是"从站明确拒绝"，重发无意义；只有 CRC/超时/帧错误才重试。
  • RS485 方向：先试内核 TIOCSRS485，拿不到再退回手动 RTS；发送必须 tcdrain 后再切回接收，否则截帧。
  • ODList 必须 index 升序：OD_find 是二分查找，0x7010 只能插在 0x7000 之后、哨兵之前；OD_ENTRY_H7010 是位置式宏，数组顺序一变就得跟着改。
  • 两处构建清单都要改：Makefile SOURCES 与 CMakeLists add_executable；测试目标同理（make test 与 ctest 各一份）。
  • RT 侧不上锁：只要 RT 里出现 pthread_mutex 就可能在 1ms 节拍里等待，seqlock 才是正解。
已知取舍：0x7010 的写入挂在里程计分支内（CO_application.c:631-645），意味着只有"本拍收到过新位置(odom_new)"才刷 IMU。真机下 0x6064 随 SYNC 周期到达，IMU 也随之刷新；电机侧 PDO 全断时 IMU 也不再写 OD——刻意让"融合"与"里程计"同生共死，避免 IMU 与已漂移的 θ 各自为政。
待硬件到位：① 实测校准 float32 字序与 RS485 方向；② 用真机数据定 α（0.98 只是起点）；③ 必要时对齐 yaw 零位与里程计 θ 零位（当前假设两者一致）。
