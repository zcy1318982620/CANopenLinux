调试三件套：GDB / Valgrind / strace · 知识讲解

工程：panasonic_canopen_agv ｜ 主题：动调（GDB）· 内存体检（Valgrind）· 系统调用跟踪（strace）
一句话分工：GDB 管"程序里发生了什么"（断点、变量、调用栈、崩溃现场）；Valgrind 管"内存用得对不对"（泄漏、越界、未初始化）；strace 管"程序跟内核说了什么"（系统调用、真正失败的原因）。三者视角互补，配合使用能定位 90% 的 Linux 应用问题。

§1 先建立直觉：三件套各自回答什么问题

工具观察层典型提问
GDB源码 / 变量 / 函数调用"崩在哪一行？这个变量当时是多少？为什么进了这个分支？"
Valgrind堆内存读写"哪里泄漏了内存？哪里越界读写？用了未初始化的值？"
strace内核系统调用边界"为什么打不开设备？卡在哪个系统调用？errno 到底是什么？"
用本工程的场景对号入座：① 程序段错误 → GDB；② 长跑后内存只涨不降 → Valgrind；③ ./canopend can0 报"打不开 CAN 设备"、但你不知道是权限还是设备不存在 → strace（一眼看清 open/ioctl 返回了什么 errno）。

§2 GDB —— 动态调试器

2.1 前提：编译时带调试信息

GDB 要能"对上源码行号、读出变量名"，全靠编译时的 -g。本工程 [Makefile L55](file:///home/zcy/Project/panasonic_canopen_agv/Makefile#L55) 已经写了 -g -ggdb，开箱可调试。若哪天换成 -O2 优化，变量可能被优化掉、单步会乱跳——调试期建议 -Og -g。

发布版要剥符号：上线时用 strip canopend 减小体积；但保留一份带符号的二进制（或单独的 .debug 文件），否则线上 core dump 无法定位。

2.2 三种启动方式

gdb ./canopend                        # 只加载，先不跑
gdb --args ./canopend can0 -i 1       # 带启动参数（推荐：参数直接跟在 --args 后面）
gdb -p 12345                          # 附加到已在跑的进程（PID=12345）

本工程是 CANopen 从站，跑起来要带设备名和节点号，所以第二种最常用：gdb --args ./canopend can0 -i 1，进去后 run（简写 r）。

2.3 常用命令（背背这张表就够用 80%）

命令简写作用

2.4 本工程实战：三步走

场景：怀疑启动时参数解析或日志初始化有问题，让程序在应用启动处停下来看看。

$ gdb --args ./canopend can0 -i 1
(gdb) b app_programStart          # 在应用启动函数下断点
(gdb) run
Breakpoint 1, app_programStart () at CO_application.c:xx
(gdb) bt                          # 看是谁调用的（应为 main → app_programStart）
(gdb) info args                   # 看传进来的参数
(gdb) n                           # 单步往下
(gdb) p nodeId                    # 打印节点号
(gdb) c                           # 继续运行

场景：多线程程序"卡死"，想看谁在等谁。Ctrl+C 让 GDB 接管后：

(gdb) info threads                # 列出主线程 + RT 线程 + 2 个工作线程
(gdb) thread apply all bt         # 每个线程的栈：谁卡在 pthread_mutex_lock / cond_wait 一目了然
结合本工程的双线程 + 日志线程池：主线程跑 epMain、RT 线程（SCHED_FIFO，1ms）跑 epRT、再加 2 个日志工作线程等待条件变量。若日志线程不消费，队列满后 RT 线程入队会丢掉记录——此时用 thread apply all bt 能看到 RT 线程是否卡在锁上，定位"日志把 RT 拖慢"的死锁/争用。

2.5 Core Dump：事后验尸

程序已经崩了、没来得及接 GDB，就靠内核生成的 core 文件复现现场。

# ① 允许生成 core（默认常为 0，即关闭）
ulimit -c unlimited

# ② （可选）看/改 core 保存路径与命名
cat /proc/sys/kernel/core_pattern

# ③ 跑程序，崩溃后得到 core 文件（如 core、core.12345）

# ④ 用 GDB 加载"二进制 + core"
gdb ./canopend core.12345
(gdb) bt                # 直接看到崩溃时的完整调用栈
(gdb) frame 1           # 切到出错的那层
(gdb) info locals       # 看现场变量
(gdb) p 变量
匹配前提：core 必须和"产生它的那个二进制"（同一 build、未改、符号一致）配对，否则栈是乱的。所以每次重新编译后旧的 core 就没用了。

2.6 gdbserver：嵌入式远程调试

目标板资源有限，不能在板上跑完整 GDB。做法：板上跑 gdbserver，主机跑 GDB 连接（第 9 站交叉部署会用到）。

# 目标板（ARM）：
gdbserver :2345 ./canopend can0 -i 1

# 主机（x86，用交叉工具链自带的 arm-linux-gnueabihf-gdb）：
arm-linux-gnueabihf-gdb ./canopend
(gdb) target remote 192.168.1.100:2345     # 连到目标板
(gdb) b app_programStart
(gdb) c
要点：主机和板上用的必须是同一份可执行文件（连调试信息一起）。GDB 在主机侧读符号，程序在板上跑——网络协议把断点、变量传过来。

§3 Valgrind —— 内存体检

原理：把程序加载进 Valgrind 的虚拟 CPU 执行（动态二进制插桩），于是每一次内存读写都被它记下来。因此不需要重新编译（但带 -g 才有文件名行号），代价是程序变慢 10~50 倍。

3.1 最基本的一条命令

valgrind --leak-check=full --show-leak-kinds=all --track-origins=yes \
         ./canopend can0 -i 1
选项作用
--leak-check=full详细报告每个泄漏块，给出分配处的调用栈
--show-leak-kinds=all连 still reachable 也列出（默认只列 definitely/possibly）
--track-origins=yes追"未初始化值"从哪来——查 Conditional jump depends on uninitialised value 必开
--log-file=vg.log报告写文件，方便长输出

3.2 报告怎么读

分类含义要不要修
definitely lost真丢了，指针没了、再也 free 不到必修（真泄漏）
indirectly lost因为持有它的对象丢了而跟着丢修好 definitely 后通常会一起消失
possibly lost指针指向块内部（非开头）多半要修，视情况
still reachable程序结束时还持有指针（如全局缓存）通常可接受，不算真泄漏
==12345== HEAP SUMMARY:
==12345==     in use at exit: 1,024 bytes in 2 blocks
==12345==   total heap usage: 40 allocs, 38 frees, 12,288 bytes allocated
==12345==
==12345== 1,024 (512 direct, 512 indirect) bytes in 1 blocks are definitely lost
==12345==    at 0x483B7F3: malloc (in vgpreload_memcheck...)
==12345==    by 0x401234: app_programStart (CO_application.c:88)   ← 分配处
==12345==    by 0x400ABC: main (CO_main_basic.c:120)               ← 调用链
==12345==
==12345== LEAK SUMMARY:
==12345==    definitely lost: 512 bytes in 1 blocks
==12345==    indirectly lost: 512 bytes in 1 blocks
==12345==    still reachable: 0 bytes in 0 blocks

看 分配处的调用栈（by ... 文件:行号）就能直接定位到哪行 malloc 没配对 free。

3.3 本工程使用注意

  • 让程序正常退出：Valgrind 在 exit 时汇总。本工程有 atexit 冲洗日志、线程池要 join——如果直接被 Ctrl+C 杀掉或段错误，报表会不完整/误报"still reachable"。
  • 慢：RT 线程 1ms 周期在 Valgrind 下会严重超时（SYNC/心跳超时会刷屏）。测内存问题时建议用 单线程模式 -DCO_SINGLE_THREAD=1 重编，或忽略实时性告警只看内存报告。
  • 不是万能：不检测栈上的静态数组越界、不检测部分竞态（那是 --tool=helgrind 的活）。
顺手一提：同一套 Valgrind 还能换工具——valgrind --tool=helgrind ./canopend ... 查数据竞争/锁误用，valgrind --tool=callgrind ./canopend ... 做性能剖析（配合 kcachegrind 看图）。面试能顺带说出这两个，加分。

§4 strace —— 系统调用跟踪

原理：用 ptrace 挂住进程，每一进/出内核的系统调用都打印出来（名字、参数、返回值）。它是"程序与操作系统之间的抓包工具"。

4.1 常用参数

参数含义场景
-f跟踪所有子线程/进程本工程必加（多线程，不加只看主线程）
-tt / -t每行加时间戳（微秒/秒）看时序、算耗时
-T每行末尾加该系统调用耗时找"慢在哪一步"
-e trace=网络只跟某类调用，如 network、file、openat降噪，聚焦
-o file输出到文件输出太多时
-s 256字符串最多打印 256 字符（默认 32）看完整路径/内容
-p PID附加到运行中的进程问题进程已在跑
-c结束时汇总各调用次数/耗时统计概览

4.2 本工程实战：为什么打不开 CAN 设备 / 卡在哪

本工程用 socketCAN：socket(PF_CAN, SOCK_RAW, CAN_RAW) → ioctl(SIOCGIFINDEX) 拿接口索引 → bind 到 can0 → epoll 等收发。用 strace 一眼看清每一步的结果：

$ strace -f -tt -e trace=network,ioctl,openat ./canopend can0 -i 1
...
socket(PF_CAN, SOCK_RAW, CAN_RAW)          = 3
ioctl(3, SIOCGIFINDEX, {ifr_name="can0", ifr_index=0}) = 0   ← 若返回 -1 ENODEV，说明 can0 不存在
bind(3, {sa_family=AF_CAN, ...}, 16)       = 0               ← 若返回 -1，看 errno（权限/接口状态）
epoll_wait(4, ...)                          = ...            ← 卡在这 = 没收到 CAN 帧
关键读法：每行末尾的返回值才是结论。= -1 ENODEV（设备不存在）、= -1 EACCES（权限不足）、= -1 EBUSY（被占用）—— 这些 errno 是 GDB 里看不到的、最直接的失败原因。本工程若报"Can't find CAN device"，strace 会把 ioctl(SIOCGIFINDEX) 的失败和 errno 直接摊开。

4.3 一个更常见的用法：看它到底卡在哪

$ strace -f -tt -T -p $(pgrep canopend)     # 附加到正在跑的进程
# 输出停在最后一行不动的那个系统调用，就是它正在等的东西：
#   卡在 epoll_wait      → 正常，在等事件
#   卡在 read/recv       → 在等数据
#   卡在 futex           → 在等锁/条件变量（结合 GDB 的 thread apply all bt 看谁持有锁）

4.4 也常用于查"文件/配置读没读到"

$ strace -e trace=openat,read -f ./canopend can0 -i 1
openat(AT_FDCWD, "/etc/...配置", O_RDONLY) = 3      # 成功打开
openat(AT_FDCWD, "/要用的文件", O_RDONLY) = -1 ENOENT   # 路径/文件不存在 → 一眼看出

§5 三件套怎么配合：按现象选工具

        现象
         │
 ┌───────┴───────────────────────────────────────────┐
 │                                                    │
 ▼ 崩溃 / 逻辑不对                          ▼ 内存涨 / 行为诡异
 GDB                                       Valgrind
 - core dump 验尸：bt → frame → info locals  - --leak-check=full 看分配栈
 - 断点 + watch 变量                        - --track-origins=yes 查未初始化
 - 多线程：thread apply all bt              - helgrind 查锁竞争
 │                                                    │
 └───────────────────────┬────────────────────────────┘
                         ▼ 还查不出来 / 程序没输出 / 卡住
                       strace
                       - -f -tt -T 看系统调用与耗时
                       - 返回值里的 errno 是终极线索
                       - 卡在哪个调用＝它在等什么
                         │
                         ▼
              交叉验证：strace 定位到"卡在 futex" →
              回 GDB `thread apply all bt` 看谁持有锁 → 定位死锁
串起来的一个真实套路：程序启动后没日志、像是卡住 → ① strace -f -p PID 发现卡在 futex（等锁）；② gdb -p PID 里 thread apply all bt，看到工作线程在 pthread_cond_wait、RT 线程在 pthread_mutex_lock；③ 检查锁的持有者——定位到"某条路径忘了 unlock"。这就是"系统调用层 + 源码层"两级观察的价值。
