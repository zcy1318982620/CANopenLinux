第 9 站 · 交叉编译 & 部署到 i.MX6ULL

本站定位：阶段 C「上位机 & 上板」的最后一站，也是十站地图里唯一还没有独立分册的一站。前八站全部发生在 PC 上（x86 编译、vcan 虚拟总线）。本站回答一个问题：怎么让这套 canopend 真正跑在 i.MX6ULL 板子上。

为什么必须自己走一遍：① 简历/话术里已经写了「部署到 i.MX6ULL 开发板」，面试官一定顺着问怎么部署的，答不上来比不写还减分；② 这是「PC 软件」和「设备固件」的分水岭——不会交叉编译，工程永远停在电脑里；③ 它顺手牵出设备树这项嵌入式门槛知识（§5），而设备树正是「应用岗只需看懂、不必会写内核」的那条边界线。

阅读顺序：§0 四步链路（先建全局）→ §1 交叉编译原理 + 本工程工具链逐行 → §2 编译与验证 → §3 部署 → §4 板端启动 → §5 设备树（重点） → §6 SocketCAN 内核链路与驱动「够用层」→ §7 面试自检 → §8 半天补课清单。

§1 为什么必须交叉编译：宿主机 / 目标机 / 工具链 / sysroot

1.1 为什么不能在板子上直接编译

  • 资源不够：i.MX6ULL 是单核 Cortex-A7 + 几十~几百 MB 内存，编 31 个文件还行，编整个内核/大型工程就是灾难。
  • 环境不全：板上的根文件系统是裁剪过的，通常没有 gcc、没有头文件、没有静态库。
  • 产物跑不动：PC 的 gcc 默认生成 x86_64 指令，板子是 ARM 指令——CPU 根本不认识。所以不是「优化问题」，是指令集不同。
表 9-2 四个必须分清的名词
名词含义（本工程对应）
宿主机 host你敲命令的 PC：Ubuntu 20.04.6 / x86_64 / gcc 9.4.0
目标机 target程序最终运行的机器：i.MX6ULL（ARM Cortex-A7，ARMv7-A，硬浮点 hard-float）
交叉工具链 toolchain跑在 x86 上、却能生成 ARM 指令的一整套 gcc/binutils：arm-linux-gnueabihf-gcc（Linaro 4.9.4-2017.01）
sysroot工具链自带的一份「目标机文件系统精华」：目标机的 libc、libpthread、头文件。用来解决「在 PC 上编译时，去哪找板子上的库」

名字里的玄机：arm-linux-gnueabihf- 拆开读——arm（目标架构）+ linux（目标系统）+ gnu（用 glibc）+ eabi（嵌入式 ABI）+ hf（hard-float，浮点参数用 VFP 寄存器传，不是软件模拟）。目标机的 ABI 必须和工具链后缀一致，否则链接/运行期出各种诡异问题。

1.2 本工程怎么切到交叉编译：toolchain-arm.cmake 逐行

交叉编译最规范的做法不是改 Makefile（那是土办法），而是给 CMake 一份「工具链描述文件」。本工程这份共 20 行，全文见 toolchain-arm.cmake。

表 9-3 toolchain-arm.cmake 逐行讲解（★ 面试高频）
行代码作用
L7set(CMAKE_SYSTEM_NAME Linux)告诉 CMake「我要编的是 Linux 程序」。这一行是「进入交叉编译模式」的总开关——CMake 检测到它与宿主系统不同，就自动停止尝试运行测试程序。
L8set(CMAKE_SYSTEM_PROCESSOR arm)目标 CPU 架构 = arm（信息性，配合上一条）。
L10set(TOOLCHAIN_PREFIX /usr/local/arm/gcc-linaro-4.9.4-2017.01-x86_64_arm-linux-gnueabihf)工具链安装路径。抽成一个变量，路径变了只改这一行。
L11-L12set(CMAKE_C_COMPILER ${TOOLCHAIN_PREFIX}/bin/arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER ...g++)		核心：把「编译器是谁」从宿主的 gcc 换成跨平台的 arm-linux-gnueabihf-gcc。
L13set(CMAKE_FIND_ROOT_PATH ${TOOLCHAIN_PREFIX}/arm-linux-gnueabihf)指定 sysroot：以后 CMake find_* 找头文件/库时，都先到这个「目标机文件系统」里找。
L14set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)「找程序」不要进 sysroot——编译过程要用的是宿主的 ld/ar 等工具，它们必须能在 PC 上执行。
L15-L16..._MODE_LIBRARY ONLY
..._MODE_INCLUDE ONLY		「找库」和「找头文件」只在 sysroot 里找——绝不能误用 PC 上的 x86 库，否则链接出的东西板子跑不了。
这三行 FIND_ROOT_PATH_MODE_* 是交叉编译最容易踩的坑。如果不设或设错，CMake 可能一边用 ARM 编译器、一边又找到了宿主机的 /usr/include 和 /usr/lib/x86_64-linux-gnu/*.so，症状是：编译能过、链接报「格式不匹配（file format not recognized）」或运行期段错误。
对照别处的做法：若不用 CMake，本工程 Makefile 也留了后门——CC ?= gcc 允许 make CC=arm-linux-gnueabihf-gcc 一行切过去。两种做法的本质相同：换编译器 + 换 sysroot，只是 CMake 把它写成了声明式文件，更规范、更可复现。

§2 编译与验证：怎么证明「这个二进制是给板子的」

2.1 两条命令完成交叉编译

# ① 配置（指定工具链文件，out-of-source 构建到 build-arm/）
cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=toolchain-arm.cmake

# ② 编译
cmake --build build-arm -j16

# 产物：build-arm/canopend   →   拷出来命名成部署用的名字
cp build-arm/canopend deploy/canopend_arm

等价的 Makefile 写法：make CC=arm-linux-gnueabihf-gcc -j16。

最常见的三个报错，先背下来：
  • Permission denied → 忘了 chmod +x。
  • No such file or directory（但文件明明在）→ 动态链接器 /lib/ld-linux-armhf.so.3 不存在。
  • ... not found (required by ./canopend_arm) 或 version `GLIBC_2.xx' not found → 板子上的 glibc 比编译时用的 sysroot 旧。解决办法：换用与板子匹配的旧工具链重编，或把库一起拷过去（用 LD_LIBRARY_PATH）。
工程现状（诚实交代）：deploy/canopend_arm 已经存在且已确认为 ARM 二进制（396235 字节），但是 AI 代为编译并拷贝上板的，本人尚未亲手复现。另外 hmi/mainwindow.cpp 里默认板卡 IP 已改为 169.254.86.72，但 HMI 未重编译验证（HANDOFF 遗留 7）。

§4 板端启动：两条命令 + 一个主站

4.1 启动序列

# ① 配 CAN 控制器：指定类型/波特率（本工程目标 500 kbit/s）
ip link set can0 type can bitrate 500000

# ② 启用这块网卡（CAN 在 Linux 里就是一块 net_device）
ip link set can0 up

# ③ 看一眼细节：波特率、状态、错误计数
ip -d link show can0

# ④ （可选）裸眼抓帧，验证总线上真有报文
candump can0

# ⑤ 启动 CANopen 主站：node id = 1，并开启 TCP 60000 的 ASCII 网关
canopend can0 -i 1 -c "tcp-60000"
表 9-6 每条命令到底在干什么
命令片段含义
ip link set can0 type can bitrate 500000通过 netlink 把「位时序参数」下发给驱动，最终调到 FlexCAN 的 CANCTRL 寄存器（内核路径见 §6）。波特率不在设备树里，是运行期设的。
ip link set can0 up启用控制器、退出 STOP 模式、开始参与总线仲裁。down 状态下无法收发。
canopend can0 -i 1把 can0 作为 CANopen 通道，本机节点号 1（主站/NMT master）。
-c "tcp-60000"开启 CiA 309-3 ASCII 网关，监听 TCP 60000，供上位机（第 8 站 Qt / cocomm）用文本命令读写对象字典。
真机联调的两个已知坑（HANDOFF 遗留）：
  • 出厂参数不是 500K：森创驱动器出厂默认为 250K、站址 1，需要先改成 500K 并与本工程两套 OD 的节点号（10 / 11）对齐。
  • 单节点会报 ERROR-WARNING：CAN 需要至少两个节点互相 ACK。只有板子自己挂在总线上时，发送无人应答会产生错误计数并进入错误被动/警告态——这不是你的代码错，接上第二个节点（或第二个 vcan 端口）就好了。

§5 设备树（Device Tree）：CAN 为什么叫 can0，谁把它打开的

这是应用岗最需要「看懂」的一块嵌入式知识。§4 里 ip link set can0 能生效，前提是内核里已经存在一个叫 can0 的网络设备——而它是从哪来的？答案就是设备树。

5.1 为什么会有设备树

早期 ARM 内核为每一块开发板写一份 board-xxx.c，把「板子上有哪些外设、引脚怎么接、时钟多少」硬编码在 C 代码里。结果是：一份内核源码里堆了成百上千块板的适配代码，改一处引脚都要重编内核。

设备树把「硬件长什么样」从代码搬到了数据：

内核（一份二进制，与板子无关）  +  xxx.dtb（这块板子的硬件描述）  →  启动时解析 → 生成 platform_device → 与驱动匹配
                                    ▲
                              编译期由 .dts/.dtsi 生成

于是：同一份内核镜像，换一个 dtb 就能支持不同的板子。引脚接法不同？改 dts。外设要关掉？改 dts。

5.2 四件套：dts / dtsi / dtb / dtc

5.3 i.MX6ULL 的 FlexCAN 节点长什么样

下面是 i.MX6UL/ULL 主线的典型写法（SoC 级 .dtsi 节选，用于理解结构；迅为板实际的引脚组以其板级 dts 为准）：

/* ===== SoC 级：imx6ull.dtsi 节选 ===== */
can1: can@2090000 {
    compatible = "fsl,imx6ul-flexcan", "fsl,imx6q-flexcan";  /* ← 驱动靠这个字符串匹配 */
    reg = <0x02090000 0x4000>;                                /* ← 寄存器基址 + 长度 */
    interrupts = <GIC_SPI 110 IRQ_TYPE_LEVEL_HIGH>;          /* ← 中断号 */
    clocks = <&clks IMX6UL_CLK_CAN1_IPG>,                    /* ← 模块时钟 */
             <&clks IMX6UL_CLK_CAN1_SERIAL>;
    clock-names = "ipg", "per";
    fsl,stop-mode = <&gpr 0x10 1>;
    status = "disabled";                                      /* ← 默认关闭，等板级打开 */
};
表 9-8 逐字段读懂一个节点（这是设备树的核心阅读能力）
字段含义对应用
compatible最重要：告诉内核「用哪个驱动」。内核里 flexcan.c 的匹配表里有 fsl,imx6ul-flexcan 这一项，两边对上，驱动才被加载★ 面试会问「驱动怎么和硬件对上」
reg寄存器物理地址范围（CAN1 基址 0x02090000，长度 0x4000）解释「ip 命令怎么最终写到硬件」的起点
interrupts中断号：收到帧时内核靠它唤醒CAN 收帧是中断驱动的
clocks / clock-names该外设用哪些时钟源，名称为 ipg（寄存器接口时钟）、per（协议时钟）解释「为什么波特率配错会报错」——位时序是从 per 时钟分频来的
status"disabled" / "okay"：这个外设开不开★★ 最常改的一行：板级 dts 里把它改成 "okay"，CAN 才存在

5.4 引脚复用 pinctrl：一个引脚有 8 种身份

SoC 的引脚是复用的：同一个物理管脚可以当 UART、可以当 GPIO、也可以当 CAN。必须显式声明「这个脚用哪个功能」，这就是 pinctrl。板级 dts 里长这样：

/* ===== 板级：xxx-xxx.dts 节选（典型写法） ===== */
&iomuxc {
    pinctrl_flexcan1: flexcan1grp {          /* ← 给这组引脚起个名字 */
        fsl,pins = <
            MX6UL_PAD_UART3_RTS_B__FLEXCAN1_RX   0x1b020   /* 该脚 → CAN1 的 RX */
            MX6UL_PAD_UART3_CTS_B__FLEXCAN1_TX   0x1b020   /* 该脚 → CAN1 的 TX */
        >;
    };
};

&can1 {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_flexcan1>;        /* ← 引用上面那组引脚 */
    status = "okay";                          /* ← 打开这一路 CAN */
};
宏名怎么读：MX6UL_PAD_<引脚>__<功能>。前半段是物理位置，后半段是分配的功能；中间的双下划线是「引脚 __ 功能」的分隔符。0x1b020 是引脚的电气配置（上下拉、驱动强度等），先会读、不必会算。右侧注释里的 RX/TX 一旦反接，总线上就永远收不到帧——这是硬件联调第一检查项。

5.5 怎么在板子上「看见」设备树

# ① 标准路径：内核解析后的设备树会以「目录/文件」形式暴露出来
ls /sys/firmware/devicetree/base/
cat /sys/firmware/devicetree/base/soc/can@2090000/status     # 看这一路开没开

# ② 老一些的内核走 procfs
ls /proc/device-tree/

# ③ 把运行中的设备树反编译回 dts（最直观）
dtc -I fs -O dts /sys/firmware/devicetree/base > /tmp/live.dts

# ④ 看驱动有没有加载、CAN 有没有注册成功
dmesg | grep -i flexcan

因果链走通一遍：设备树描述硬件 → 内核据此生成设备 → 驱动被 compatible 匹配上 → 注册出网络设备 → 用户空间看到 can0。这条链想清楚，你就真正理解了 ip link set can0 为什么能生效。

5.6 改设备树的标准流程

① 找到板级 dts（板厂提供的通常是 xxx-xxx-emmc.dts）
② 改内容（如把 &can1 的 status 改 "okay"、改/加 pinctrl 组）
③ 重新编译出 dtb：在内核源码树里 make dtbs
   （或单独编：dtc -I dts -O dtb -o new.dtb board.dts）
④ 把新 dtb 替换到启动分区（u-boot 从那里加载）
⑤ 重启板子，dmesg 里确认驱动起来了
边界：应用岗改到哪一层就够了？看懂节点、改 status、改引脚组、会反编译查看——到这里为止。再往下（写一个新驱动的 character device、改 flexcan.c、写内核模块）属于驱动/BSP 岗，不是你这次要补的。
把设备树和你的项目挂上钩（面试话术）：「Linux 应用层看到的 can0 是一个标准网络设备，它由设备树里的 FlexCAN 节点声明、由 pinctrl 指定引脚、由 compatible 匹配到内核驱动。所以我们的 canopend 完全不用碰硬件细节——它只做 SocketCAN 读写，硬件差异都被设备树和驱动屏蔽掉了。这也是嵌入式 Linux 应用开发能高效迭代的原因。」

§7 面试自检：这 8 个问题必须能自己答

7.1 部署五问（本站主线）

  1. 为什么要交叉编译？板子资源小、没编译器；PC 的 gcc 产出的 x86 指令板子不认识，必须在 x86 主机上生成 ARM 指令。
  2. 你们用的什么工具链，toolchain-arm.cmake 改了哪几项？arm-linux-gnueabihf-（Linaro 4.9.4）；改的是 CMAKE_SYSTEM_NAME/PROCESSOR、CMAKE_C_COMPILER、CMAKE_FIND_ROOT_PATH（sysroot）三处。
  3. sysroot 是干什么的？ PC 上编译时，头文件和库不能取自宿主机，必须指向「目标机版本的库」，否则链接出 x86 的 .so。
  4. 怎么证明编出来是给板子的？file 看到 ELF 32-bit ARM EABI5、解释器 /lib/ld-linux-armhf.so.3；再 readelf -A 确认硬浮点 ABI。
  5. 二进制怎么到板子、板端怎么启动？scp（或 NFS/tf 卡）+ chmod +x；板端 ip link set can0 type can bitrate 500000 → ip link set can0 up → canopend can0 -i 1 -c "tcp-60000"。

7.2 设备树三问（延伸）

  1. can0 这个网卡是怎么来的？设备树里 FlexCAN 节点 status = "okay"，内核按 compatible 匹配到 flexcan 驱动，注册出网络设备，用户空间才看到 can0。
  2. 波特率写在设备树里吗？不写。设备树负责「有没有这个控制器、引脚对不对」，波特率由运行期 ip link set ... bitrate 经 can-dev 下发给驱动。
  3. 设备树和驱动怎么绑定？靠 compatible 字符串做匹配：节点写 "fsl,imx6ul-flexcan"，驱动里也有同名匹配项，两边对上就 probe。
再补一句能加分的：「我们应用层的 canopend 只依赖 SocketCAN 这套标准接口，硬件差异（引脚、时钟、寄存器）全被设备树和内核驱动屏蔽了。这就是嵌入式 Linux 应用开发的价值——同一份应用代码，换块板子重编一次即可。」
