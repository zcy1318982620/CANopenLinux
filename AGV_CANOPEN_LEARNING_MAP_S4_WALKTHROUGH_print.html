第 4 站 · PDO 映射 & CiA402 —— 运行时的数据怎么跑

工程：panasonic_canopen_agv —— 松下「実験用 AGV」双轮差速底盘，基于 CANopenNode V4 的 CANopen 从站（Linux 用户态 + SocketCAN，进程名 canopend）。双对象字典：OD（右电机）/ OD_2nd（左电机）。

0. 一页地图：第 4 站也只有两条链

先给一句话结论：PDO 是「运行时的数据通道」——它不像 SDO 那样一问一答，而是周期性地、一帧把好几个数据打包送出去/收进来。快，但代价是：只能传「提前配置好映射关系」的那几个对象。所以第 4 站的全部内容，就是「配置怎么把这些数据绑上通道」+「运行时帧怎么变成应用里的值」。

1. PDO 是什么：运行时的「数据高速公路」

1.1 一句话原理

PDO = Process Data Object，过程数据对象。它的设计目标只有一个：快。为了快，它放弃了 SDO 的灵活性——帧里不带索引、不带子索引，只有「裸数据」。那接收方怎么知道每个字节是什么？靠开机时双方约定好的「映射表」：这条帧按固定顺序装哪几个对象、每项占多少位，事先写进 OD 的 PDO 配置对象里。运行时只发裸数据，靠位置对应关系还原。

一句话对比记忆：SDO = 带门牌的快递（慢但送哪都行）；PDO = 定好格子的流水线（快但只能装约定的东西）。

1.2 两个方向：RPDO 与 TPDO

2. PDO 的「四件套」：四个配置对象

每一条 PDO 都靠 两个 OD 对象来描述：一个说「这条帧用哪个 CAN-ID、什么时候发/收」，另一个说「帧里装哪几个 OD 对象」。加上收发两个方向，就是四件套。

表 2-1　PDO 四个配置对象（索引范围，本项目都只用第 0、1 号）
索引名字管什么本项目用法
0x1400~0x1403RPDO 通信参数RPDO 的 CAN-ID、传输类型、事件定时器右电机用 0x1400（COB-ID 0x38A）；左电机用 0x1401（COB-ID 0x38B）
0x1600~0x1603RPDO 映射参数RPDO 里装哪几个对象、每项多少位右电机 0x1600、左电机 0x1601，都映射 0x6041+0x6064
0x1800~0x1803TPDO 通信参数TPDO 的 CAN-ID、传输类型、抑制/事件时间未使用
0x1A00~0x1A03TPDO 映射参数TPDO 里装哪几个对象未使用

2.1 「通信参数」对象里有哪几个子索引

以 RPDO 的 0x1400 为例（TPDO 的 0x1800 类似，只是多两项）。子索引 0 是这个对象的「成员个数」，子索引 1 起才是真正的配置值——这是 CANopen 里 REC（记录型）对象的通用规矩，第 3 站讲过。

0x1400  RPDO 通信参数（右电机）
 ├─ sub0 : 成员个数（= 5，说明下面有 5 项）
 ├─ sub1 : COB-ID        ← 这条 PDO 用哪个 CAN 帧号 + 是否启用   ★最重要
 ├─ sub2 : transmissionType ← 传输类型：同步(跟 SYNC)还是事件驱动
 ├─ sub3 : inhibitTime    ← 抑制时间（两条帧之间至少隔多久）本项目未用
 ├─ sub4 : （保留）
 └─ sub5 : eventTimer     ← 事件定时器：多久没收到就当超时（本项目 0=不启用）

0x1800  TPDO 通信参数（对比：多两项）
 ├─ sub0 : 成员个数
 ├─ sub1 : COB-ID
 ├─ sub2 : transmissionType
 ├─ sub3 : inhibitTime
 ├─ sub4 : （保留）
 ├─ sub5 : eventTimer
 └─ sub6 : SYNC 起始值   ← TPDO 才有的「第几个 SYNC 发一次」

2.2 「映射参数」对象里装了什么

以 RPDO 的 0x1600 为例。sub0 是「映射了几项」，sub1、sub2…… 每一项是一个 32 位数，描述「装的是哪个 OD 对象、多少位」。

0x1600  RPDO 映射参数（右电机）
 ├─ sub0 : 映射项数 = 2          ← 说明这条帧里装 2 个对象
 ├─ sub1 : 0x60410010            ← 第 1 项：0x6041(状态字)、16 位
 ├─ sub2 : 0x60640020            ← 第 2 项：0x6064(实际位置)、32 位
 └─ sub3.. : 0（没用到的位置留空）

  → 这条帧一共 16 + 32 = 48 位 = 6 字节，装「状态字 + 实际位置」两样东西。
数量必须对得上：sub0 写的「几项」必须和后面真正填了的项数一致，且所有项总位数不能超过一帧能装的量（经典 CAN 单帧最多 8 字节）。写错会报 CO_EM_PDO_WRONG_MAPPING（§4 会看到）。

3. 三个「配置值」怎么读

配置时只需要看懂三种值。它们看着像乱码，其实都是从高位往低位分段拼出来的。（本节只讲语义怎么拆，不做逐字节拆帧。）

3.1 映射项：一个整数里塞了「索引 + 子索引 + 位长」

映射项是一个 32 位数，从高到低分成三段：

映射项 = 0x60410010   （32 位）
 ┌──────────────┬─────────┬────────────┐
 │  高 16 位     │ 中 8 位  │  低 8 位    │
 │  0x6041      │   0x00  │    0x10    │
 │  = 索引       │ = 子索引 │ = 位长(16) │
 └──────────────┴─────────┴────────────┘
 读作：把 OD 里「索引 0x6041、子索引 0、占 16 位」的那个对象，装进这条帧。

再对照两条：
   0x60410010 → 0x6041 : 0，16 位   （状态字，本来就 16 位）
   0x60640020 → 0x6064 : 0，32 位   （实际位置，本来就 32 位；低 8 位 0x20 = 32）

 （低 8 位是「位」不是「字节」：16 位=2 字节，32 位=4 字节。）

3.2 传输类型 transmissionType：这条帧什么时候动

表 3-1　transmissionType 的取值含义
取值含义
0 ~ 240同步：跟着 SYNC 节拍走。0=收到 SYNC 就更新；1~240=每 N 个 SYNC 更新一次。（同步 PDO 才会有「两个接收缓冲、交替使用」的机制。）
254 / 255事件驱动（异步）：不跟 SYNC，数据一到就处理/发送。本项目 RPDO 初值就是 254，所以每收到一帧就立刻处理，不等 SYNC。
其它252/253 与 RTR 相关，本项目用不到。

3.3 COB-ID：用哪个 CAN 帧号，以及「是否启用」

COB-ID 是一个 32 位数，但只有低 11 位是真正的「CAN 帧号」，最高位另有含义：

   0x0000038A  →  bit31=0（启用）  低 11 位 = 0x38A   读作：启用，用 CAN-ID 0x38A
   0x80000300  →  bit31=1（禁用）  低 11 位 = 0x300   读作：这条 PDO 先关着，别用

 ★ 关键：本工程 OD 里 0x1400 的 COB-ID「出厂值」是 0x80000200 ——高位是 1，意思是默认关闭；
   必须由 app_programStart() 改写成 0x0000038A 才是「启用 + 用 0x38A」。这一步没做，帧就收不到。
坑 1：COB-ID 低 11 位不能是 0，也不能用协议保留的高优先级帧号（0x000~0x080 那几个 NMT/SYNC/EMCY 专用号）。校验不过 CO_RPDO_init 会把它当非法，直接报文 CO_ERROR_OD_PARAMETERS 或把这帧判为无效。
坑 2：「通道配好了」和「通道开着」是两回事。0x80000000 这一位就是总开关，忘了解开会一直静默，很难查。

4.1 一个容易混的点：PDO 配置对象自己也挂着钩子

除了我们给 0x6064 挂的「打印钩子」，CO_RPDO_init 末尾还给 0x1400、0x1600 也各挂了一个钩子（:748-755）。作用不是打印，而是让 PDO 支持运行时改配置：

0x1400（通信参数）挂 OD_write_14xx
    → 以后有人（比如主站用 SDO）改 0x1400:1 的 CAN-ID，
      会被拦下来：校验新帧号 → 重新调 CO_CANrxBufferInit 换过滤器 → 再落盘

0x1600（映射参数）挂 OD_write_PDO_mapping
    → 有人改映射项时，重新检查项数/位长是否合法

本项目没用到运行时改配置，但这段代码解释了：为什么 PDO 的配置既能开机写、也能运行中改（都是同一套钩子机制）。

5.1 「收下 → 举手 → 主循环处理」：和 NMT / SDO 是同一套节拍

注意 CO_PDO_receive 不在回调里直接写 OD，只做「抄数据 + 举旗」；真正的 OD_IO->write() 发生在 CO_RPDO_process 里。这样设计的理由和第 2/3 站一样：收帧可能发生在内核/驱动上下文，不能在那里干重活；举旗后交给固定节拍的主循环慢慢处理。while (CO_FLAG_READ(...)) 还顺手解决了「处理期间又来了新帧」——处理完再看旗子，有就再来一遍，永远拿最新数据。

5.2 重要区别：PDO 走「实时线程」，SDO 走「主线程」

这是第 4 站和第 3 站在结构上最大的不同。同一个进程有两条处理路径：

主线程（普通优先级）                         RT 线程（实时优先级，realtime=true）
 loop{ CO_epoll_processMain(…) }             loop{ CO_epoll_processRT(…) }
        │                                            │
        ▼                                            ▼
  CO_process()  CANopen.c:1293                CO_process_SYNC()
    ├─ CO_CANmodule_process（收发搬运）           CO_process_RPDO()   ← PDO 在这里
    ├─ CO_NMT_process（网络管理）                 CO_process_TPDO()
    ├─ CO_EM_process（紧急报文）
    ├─ CO_SDOserver_process  ← SDO 在这里
    └─ 心跳 / 时间 / 网关

 一句话：周期性强、要准时的 PDO/SYNC 交给实时线程；偶尔发生、不赶时间的 SDO/NMT 放主线程。
 ★ 注意：CO_process()（主路径）里「没有 PDO」。找 PDO 要去 CO_epoll_processRT()。
为什么这么分？AGV 跑起来时，位置/速度这类数据每毫秒都在更新，晚一拍就可能影响控制；而「改个参数」晚几十毫秒无所谓。把 PDO 放到实时线程，是为了让它在调度上更优先、更准时——这正是第 6 站「实时性改造」要接着深挖的点。

7. CiA402 是什么：伺服驱动的「标准语言」

7.1 一句话原理

CANopen 允许各家设备自定义数据格式，但那样每家电机都不一样、没法通用。于是 CiA 协会定义了设备行规（Device Profile）：约定好「伺服/变频驱动这类设备」的 OD 该有哪些对象、每个对象什么含义。CiA402 就是「伺服驱动」的行规。凡自称兼容 CiA402 的驱动器，都用同一套对象号——所以本工程虽然换了品牌/型号，代码里 0x6041、0x6064 这些号仍然通用。

7.2 最该认识的那几个对象

7.3 状态机：控制字与状态字怎么配合「点着火」

伺服不是一上电就能转的，要按 CiA402 状态机一步步「点火」。规律是：我通过控制字 0x6040 的某些位下命令；驱动器把当前处于哪一步，反映在状态字 0x6041 的某些位上。这就是一种握手。

CiA402 上电启动顺序（简化：只画主路；左边是「我发的命令」，右边是「它回的状态」）

   Not ready to switch on
            │  （驱动器自检完成）
            ▼
   Switch on disabled  ──控制字 bit7=1（Fault reset，清故障）──▶ 若在 Fault，清回这里
            │  控制字 = Shutdown（bit2 quick stop=1 等组合）
            ▼
   Ready to switch on
            │  控制字 = Switch on（bit0=1）
            ▼
   Switched on
            │  控制字 = Enable operation（bit3=1）
            ▼
   Operation enabled  ◀── 只有到这里，电机才真正「使能」，能按目标走
            │  控制字 bit3=0 → 回到 Switched on
            │  控制字 bit2=0 → 走 Quick stop
            ▼
        （任意状态）出错 ──▶  Fault ：需要写 bit7=1（Fault reset）清除，再从头来

 用到的控制字位：bit0=Switch on  bit1=Enable voltage  bit2=Quick stop  bit3=Enable operation  bit7=Fault reset
 对应的状态字位：bit0=Ready to switch on  bit1=Switched on  bit2=Operation enabled  bit3=Fault
现状提醒：本项目目前没有实现这套状态机的驱动逻辑——它只收了 0x6041（状态字）和 0x6064（位置）并打印。0x6040 这些对象在 OD 里存在，但没被使用。要真正「使能电机并下达运动目标」，正是这个底座上要长出来的增量（可放到第 5/7 站之后）。

8. 小结 · 自测 · 衔接

8.1 一页复盘

① PDO = 运行时的周期性数据通道。快，但只能传「提前映射好」的那几个对象；
   RPDO 收、TPDO 发；本项目只收不发。
② 每条 PDO 靠两个 OD 对象描述：通信参数（0x1400/0x1800，管 CAN-ID/传输类型）
   + 映射参数（0x1600/0x1A00，管装哪几个对象、每项多少位）。
③ 映射项 0x60410010 是「高16位=索引 / 中8位=子索引 / 低8位=位长」拼出来的；
   传输类型 ≤240 同步、254/255 事件驱动；COB-ID 最高位=1 表示「禁用」。
④ 配置链：app_programStart 写参数+挂钩子 → CO_CANopenInitPDO → CO_RPDO_init
   → PDOconfigMap 解析 → CO_CANrxBufferInit 注册接收过滤器。先挂钩子后解映射，所以钩子生效。
⑤ 运行链：帧到 → CO_PDO_receive（收下+举旗）→ RT 线程 CO_epoll_processRT
   → CO_process_RPDO → CO_RPDO_process（写 OD）→ 命中 H6064_write → 打印 posR/posL。
   ★ PDO 在 RT 线程，SDO/NMT 在主线程 —— 这是本项目两条处理路径的分工。
⑥ CiA402 = 伺服驱动的标准对象集（0x6040 控制字 / 0x6041 状态字 / 0x6064 位置…），
   规定了一套「控制字位命令 + 状态字位反馈」的状态机。本项目暂未驱动它。
